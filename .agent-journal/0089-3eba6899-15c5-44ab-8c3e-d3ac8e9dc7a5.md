## The key insight about Pi's context model

Pi gives you three distinct injection points, and a good memory system uses all three for different reasons:

| Hook | Fires | Gets | Persisted? |
|---|---|---|---|
| `before_agent_start` | once per user prompt | `prompt`, `systemPrompt`, `systemPromptOptions` | yes — returns a `message` stored in the session |
| `context` | **before every LLM call** | deep copy of `messages`, safe to mutate | no — ephemeral, per-call |
| `session_before_compact` | on threshold/overflow/`/compact` | `preparation`, can return a custom `summary` | yes — becomes the `CompactionEntry` |

`context` is the real lever for "custom context construction" — it's the only hook that runs on *every* call and lets you both inject and prune non-destructively. `before_agent_start` is for things that should live in the transcript permanently.

## Architecture

Memory as **files on disk**, not a vector DB. One fact per file under `<workspace>/.gizmo/memory/`, plus a `MEMORY.md` index of one-line pointers. This gives you: git-diffable, user-editable, no embedding infra, and — critically — the index is cheap enough (a few hundred tokens) to sit in context *always*, with full bodies loaded on demand.

```
.gizmo/memory/
  MEMORY.md              ← index, always in context
  auth-uses-clerk.md     ← body, loaded on retrieval
  prefers-tabs.md
```

### Write path — tools

Register `memory_write` / `memory_delete` via `pi.registerTool()`. Use `promptSnippet` and `promptGuidelines` so the tool self-documents into the system prompt's `Available tools` and `Guidelines` sections rather than you hand-rolling prompt text:

```ts
pi.registerTool({
  name: "memory_write",
  promptSnippet: "Persist a durable fact about the user or project",
  promptGuidelines: [
    "Use memory_write when you learn something that will still matter in a future session.",
  ],
  parameters: Type.Object({ name: Type.String(), type: StringEnum([...]), body: Type.String() }),
  async execute(id, params, signal, onUpdate, ctx) { /* write file + update index */ },
});
```

### Read path — `context`, not `before_agent_start`

```ts
pi.on("context", async (event, ctx) => {
  const injected = { role: "user", content: renderMemoryBlock(await recall(event.messages)) };
  return { messages: [event.messages[0], injected, ...event.messages.slice(1)] };
});
```

Two things this buys you that `before_agent_start` can't:

1. **Recall re-runs mid-turn.** The agent reads three files, and the next LLM call can now surface a memory that wasn't relevant at prompt time.
2. **Injection stays out of the session log.** Memory text never accumulates in the transcript, so it never gets summarized into a compaction and duplicated.

The cost is cache invalidation — inserting after the system prompt busts the prompt cache on every change. Mitigate by keeping the block **stable within a turn** (compute recall once per `turn_start`, reuse it across the turn's calls) and placing it at a fixed position.

Use `before_agent_start` only for the always-on part — append the `MEMORY.md` index to `event.systemPrompt`:

```ts
return { systemPrompt: event.systemPrompt + "\n\n" + memoryIndex };
```

### Retrieval

Start with the index-in-prompt + explicit `memory_read` tool, and let the model do retrieval. It's dramatically better than naive keyword matching and costs one round-trip. Add a cheap lexical prefilter in `context` (score index lines against the last user message + recently-touched file paths, inject top-N bodies) only if you measure the model failing to call `memory_read`. Skip embeddings until you have >200 memories.

### Compaction is the harvest point

This is the part most memory systems miss. Compaction is exactly the moment where "what mattered in the last 100k tokens" is being computed — reuse it:

```ts
pi.on("session_before_compact", async (event, ctx) => {
  // let Pi generate its summary, then mine it for durable facts
});
pi.on("session_compact", async (event, ctx) => {
  await harvestMemories(event.compactionEntry.summary);
});
```

Why one-fact-per-file rather than a single JSON blob or SQLite:

- **Editable.** A user can open, fix, or delete a wrong memory in their editor. With a blob they can't, and wrong memories are the main failure mode of these systems.

- **Concurrency-safe by construction.** Two sessions writing different facts touch different files. With a blob, every write is a read-modify-write race — and `SessionRuntimePool` keeps up to 24 sessions live at once.
- **Deletion is cheap.** `rm` the file. No compaction, no tombstones.

`MEMORY.md` is **derived, never authored** — regenerate it from the frontmatter after every write. If a user hand-edits it, the next write clobbers them, which is the right tradeoff versus letting index and bodies drift.

## Two layers

**Layer 1 — the journal.** Append-only, per project, never rewritten. At each compaction and each session end, the message span that just left the live context gets normalized and appended as a segment. This is the authoritative record and it is the only thing that is never lossy.

**Layer 2 — the knowledge layer.** Derived facts, decisions, and relations. Every fact **cites the journal segments it came from**. Facts are mutable — they get superseded, merged, contradicted. The journal never is.

The citation link is what makes this work rather than being a fancier fact-bag. When a fact looks wrong, you can pull the actual conversation that produced it. When facts conflict, recency in the journal arbitrates. And when the knowledge layer inevitably rots, you can throw it away and re-derive it from the journal — which you cannot do with a fact-bag.

## The extraction pass is a reconciliation pass

This is where these systems live or die. The naive version — "summarize this segment into facts, append them" — degrades badly: at 50 sessions you have four contradictory memories about the auth system and no way to tell which is live.

The prompt has to be **reconcile**, not **extract**. Feed it three things:

1. the new journal segment
2. the *current* `KNOWLEDGE.md` index
3. the full bodies of any facts the segment plausibly touches (lexical prefilter on file paths + identifiers mentioned in the segment)

And ask for a diff, not a list — emit `{ create, update, supersede, merge }` operations. A decision that reverses an earlier one must produce `supersede`, which flips the old fact to `status: superseded` rather than deleting it. Superseded facts stay on disk, drop out of the index, and remain reachable through the journal. That's your audit trail for "why did we change our mind."

Two rules worth enforcing in the prompt:

- **Prefer updating an existing fact to creating a new one.** Left alone the model creates; you have to push it toward merge.
- **Record the decision and its reasoning, not the narrative.** "Considered X, chose Y because Z" is durable. "Fixed the bug in `foo.ts`" is already in git.

Use `session_compact` rather than `session_before_compact`: the "before" hook wants a return value synchronously-ish and blocks the agent, and you don't want a second LLM call sitting between the user and their next turn.

Don't let it be the only path. Journal the tail span there, but also **journal opportunistically at `turn_end` once an un-journaled span exceeds a threshold** (say 25k tokens), so an abandoned session loses at most one span. ## Retrieval

`KNOWLEDGE.md` sits in the system prompt via `before_agent_start` — current facts only, one line each. Two tools on top:

- `memory_read(name)` — full fact body plus its citations
- `journal_search(query)` — grep the segments, return matching excerpts with segment ids

The journal is deliberately *not* in context. It's the thing you go look at when a fact is disputed or when the model needs the actual reasoning behind a decision. Making it retrievable-on-demand rather than injected is what keeps this affordable.

## What this costs, honestly

One extra LLM call per compaction, with an input of roughly (normalized segment + touched facts). On a long session that's maybe 15–30k input tokens every compaction. Run it on a cheap model — reconciliation is a structured-extraction task, not a reasoning task, and Haiku handles it well. Run it **async, after the compaction returns**, so it never sits in the user's latency path; if it fails, the journal segment is still on disk and you can re-reconcile later. That failure-independence is the main reason to keep the two layers separate in the first place.

The one thing to plan for now: periodic full re-derivation. Every N segments, or on demand, rebuild `facts/` from the journal from scratch. Incremental reconciliation drifts — this is your reset button, and it only exists because the journal is authoritative and complete.

## Where it lands right now

## Is JSONL + raw markdown right?

Mostly yes, with one part I'd change.

**Markdown segments: keep.** Three reasons that actually hold:

1. The consumer is a language model. Markdown is what it reads best, with no parse or escape layer between storage and prompt. Storing raw `AgentMessage` JSON and re-rendering at read time buys nothing and costs a serialization round-trip on every retrieval.
2. It's greppable and human-inspectable. When a derived fact looks wrong, you `rg` the journal and read the actual conversation. That debugging loop is the main thing the journal exists for.
3. Append-only means the usual objection to files — update cost, rewrite races — never applies.

And there's a justification I couldn't have made before the archive change: **the journal is now allowed to be lossy.** The raw JSONL survives in `sessions/archived/`, so normalization dropping 90% of tool output isn't destroying the last copy. The journal is a derived, readable projection; the archive is the true raw. Before archiving, aggressive truncation would have been throwing away evidence.

**`index.jsonl`: this is the weak part, and you're right to poke at it.** It duplicates the frontmatter that's already in every segment file, so there are two sources of truth that can disagree — exactly the failure mode the design is supposed to avoid. I kept it because `lastEntryIdFor()` runs on every append and scanning N files to answer it is silly.

The fix is small: keep the file, but declare the frontmatter authoritative and the index a **rebuildable cache**, plus a `rebuildIndex()` that regenerates it by scanning segment frontmatter. Then a corrupt or deleted index is a non-event rather than data loss, and the "two sources of truth" objection goes away because one of them is disposable. That needs a frontmatter parser, which the store doesn't have yet — `renderSegment()` writes YAML by hand and nothing reads it back.

> **Files are the source of truth. SQLite is a derived index you can delete.**

## The fork bug

Replaced session-keyed lookup with `resumeAfter(entries)` (`journal-store.ts:111`): it collects every segment's `lastEntryId` **project-wide** and walks the branch backwards for the newest match. Since forking preserves entry ids while changing the session id, matching on entry ids means a fork resumes exactly where its parent left off instead of re-journaling everything it inherited. Test pins it directly.

Bounded residual: if you fork from a point *inside* an already-journaled segment, the entries between the fork point and that segment's end get recorded twice. Storing every entry id per index line would make it exact, but that bloats the index for a rare case — no gaps either way, which is the property that matters.

## Wiring — `src/pi-extensions/memory-journal.ts`

Four hooks:

| Hook | Records |
|---|---|
| `session_compact` | span up to `firstKeptEntryId` — ends exactly where context resumes |
| `session_before_tree` | the branch about to be abandoned |
| `turn_end` | tail past 96KB, crash insurance |
| `session_shutdown` | whatever's left |

`session_before_tree` also closes the abandoned-branch gap I flagged earlier — that's the only moment `getBranch()` still describes the branch you're leaving. Every handler is wrapped so a journaling failure logs and never touches the session. `GIZMO_MEMORY_JOURNAL=0` disables it.

Loaded via `journalExtensionPath()` prepended to `additionalExtensionPaths` (`pi-session-factory.ts:79`) — bundled rather than discovered, so memory is on by default rather than something you configure per project.
