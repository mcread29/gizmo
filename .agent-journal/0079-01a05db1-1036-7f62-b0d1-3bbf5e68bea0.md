## Findings

The current project-runtime path is generic in name but still single-owner and Unity-shaped end to end:

- `packages/extensions/src/project-service.ts`
  - `CompositeProjectService.#first()` routes by “first call that does not throw,” not by extension identity.
  - A real failure can fall through to another service and be masked.
  - Different operations for the same path can resolve to different services.
  - `revertFile` is incorrectly coupled to an external runtime service.
- `apps/agent-server/src/server.ts`
  - Creates every installed service globally, regardless of workspace enablement.
- `apps/agent-server/src/transport/project-watch-coordinator.ts`
  - Owns one watched project per connection.
  - Repeating a watch for the same path with a new session preserves the original callback’s `sessionId`, so subsequent events can be attributed to the wrong session.
- Protocol is explicitly Unity-shaped:
  - `projectStatusSchema = unityStatusSchema`
  - fixed Unity states and CLI fields (`command`, `instances`, `errors`, `warnings`)
  - `project.open` returns `UnityOpenProjectResult`
  - `project.status.changed` validates against `unityStatusSchema`
- App state is singular:
  - `projectStatus`, `projectOpening`, `projectError`, `statusLoading`
  - `hasProjectStatus` only answers whether *some* enabled extension wants the one shared service.
  - `openSelectedProject()` interprets Unity’s `ok`, `state`, `errors`, and `stderr` in core app code.
- The installed registry duplicates the server contract in
  `packages/unity/src/server/contracts.ts`; changing `@gizmo/extensions` alone will not update Unity.
- The current uncommitted peer-inspector/`enabledExtensionIds` work removes UI ownership, but status/open remain the next single-owner layer.

## Recommended bounded implementation

Introduce an **extension-keyed project-service registry with opaque status payloads**. Do not move status/open into `project.extension.invoke` yet; that would also require centralizing browser runtime lifecycle and command contributions, making the change substantially larger.

```ts
interface ProjectService {
  getStatus(projectPath: string): Promise<unknown>;
  watchStatus(
    projectPath: string,
    listeners: { status(status: unknown): void },
  ): Promise<unknown>;
  /** Resolve on success; reject with an owner-generated message on failure. */
  openProject(projectPath: string): Promise<void>;
  dispose(): void;
}
```

Replace `CompositeProjectService` with an ID-keyed registry constructed from:

```ts
{ extensionId: extension.id, create: extension.createProjectService }
```

Operations must resolve the exact requested ID—never probe/fall through. The registry should:

- reject duplicate IDs;
- verify the service is enabled for the workspace;
- lazily create per-connection instances;
- isolate disposal failures;
- support stopping/discarding one service instance when its watch is removed.

### Wire contract

Keep the existing request names but make ownership explicit:

```text
project.status { projectPath, extensionIds: string[] }
project.watch  { sessionId, projectPath, extensionIds: string[] }
project.open   { projectPath, extensionId }
```

Status/watch result:

```ts
{
  services: Array<
    | { extensionId: string; status: unknown }
    | { extensionId: string; error: { message: string } }
  >;
}
```

Event:

```ts
{
  type: "project.status.changed";
  sessionId;
  projectPath;
  extensionId;
  status: unknown;
}
```

Batch status/watch is important: it lets the coordinator atomically reconcile the complete enabled set and prevents stale watches for extensions no longer enabled. One failing service must not prevent other service snapshots from arriving.

`project.open` should return no extension payload. Unity interprets its own CLI result and throws on failure before crossing the host boundary.

### App state

Replace the singular fields with immutable keyed state:

```ts
projectServices: Record<string, {
  status?: unknown;
  loading: boolean;
  opening: boolean;
  error?: string;
}>
```

Use `$state.raw` and immutable replacement because these are opaque API responses.

Expose generic methods:

```ts
refreshProjectServices()
refreshProjectService(extensionId)
openProjectService(extensionId)
```

Replace `hasProjectStatus` with an extension capability such as `projectService: true`. Unity reads and parses only `projectServices.unity.status`; core never knows Unity status fields.

### File revert

Remove `revertFile` from `ProjectService`. It is a workspace file operation, not an editor-runtime capability. Move path containment, file reading/writing, and `revertPatch` use into an agent-server-owned project file service. This also allows Git revert in non-Unity workspaces.

## Compatibility

- This is a protocol-breaking change; increment protocol version `25 → 26`. The protocol already requires exact versions, so failing clearly is preferable to silently misrouting.
- Core app/server and the installed Unity registry bundle must be updated together. The registry’s local `contracts.ts` means workspace type-checking will not catch drift automatically.
- Old Unity web bundles expect singular `projectStatus`, `projectOpening`, and `projectError`. Without a browser-host API negotiation mechanism they will fail at runtime. For this bounded change, require rebuilding/relinking the registry and document the minimum compatible registry revision.
- Deprecated Unity protocol parsers can remain exported for one release, but they should not participate in live transport.
- Do not retain an optional “if no extension ID, choose the only service” fallback; that recreates the same single-owner ambiguity.
- Validate workspace enablement server-side, not only through `enabledExtensionIds`, so a direct client cannot invoke a disabled service.
