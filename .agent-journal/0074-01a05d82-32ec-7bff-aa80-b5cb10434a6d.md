It should not. This is transitional design debt.

Currently:

1. `workspace-view.ts` selects the **first active extension** implementing `createView()`.
2. Unity implements `createView()`.
3. Unity’s view supplies workspace metadata *and* a `panel`.
4. `WorkspaceInspector.svelte` treats that panel as the primary inspector tab.

So Unity “ownership” is accidental: the architecture conflates **describing workspace context** with **contributing inspector UI**. It is also order-dependent—another `createView()` extension could become the owner instead.

The cleaner model is:

- The app always owns `WorkspaceView` and the inspector shell.
- Extensions contribute peer-level tabs.
- Unity contributes **Status** and **Console** like any other extension.
- Subagents, Workflows, Git, and Activity contribute their own peer tabs.
- Workspace metadata/status contributions are separate from panel contributions.

My previous fix prevents unrelated tabs from nesting under Unity, but preserves that underlying compromise. A proper refactor should remove `panel` from `WorkspaceView` and stop selecting a first-owner extension.
