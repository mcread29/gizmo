**1. Virtual list offsets** (`MessageList.svelte`, new `transcript-settle.ts`)
Each mounted row now gets a resize observer that re-measures it and bumps a counter the virtual items and total height derive from. A row that grows while streaming re-renders every row below it, so nothing overlaps until the next scroll. The settle-to-bottom logic moved into its own module to keep the component under the line limit.

**2. Whitespace-only reasoning**
The Pi event translator drops thinking deltas that are only whitespace until real text arrives, and the reasoning block trims before deciding to render. A model that opens a thinking block with a newline and says nothing no longer shows an empty "Reasoning" heading. Covered by a translator test.

**3. Registry live reload**
- Server: new `extension-catalog.ts` holds the boot-time merge in one helper, with linked extensions winning over configured ones. Boot and the four registry mutations, link, unlink, update, remove, all go through it. The extension host takes a catalog getter instead of a fixed array, and its per-workspace descriptor cache is keyed on the catalog identity so a rescan is never answered from the old list.
- Client: a successful registry action now calls `reloadExtensions`. A failure there is logged and does not mask the action's own result, which is tested both ways.
- ESM cache decision: `registryUpdate` stays stale until restart. Node caches the whole module graph for an unchanged path, and busting only the entry would run new entry code against old dependencies. There is a comment at the call site. The once-per-boot project service registry limitation is also commented in `server.ts`.

**A regression I caught and fixed along the way.** My earlier quiet reconnect skipped what a thread switch does after its snapshot, so a reconnect to a new server process never re-armed the project watch, model catalog, or commands. ## assistant

Yes, a handful of things I saw along the way and left alone.

- **A `marked` renderer crash floods the console.** Every markdown render with a link throws `Cannot read properties of undefined (reading 'parseInline')` from `apps/app/src/lib/features/conversation/markdown.ts:32`. The custom link renderer uses `this.parser`, which newer `marked` versions no longer bind. There were hundreds of these in the console. Links still render because marked catches it, but it is noise and likely costs time on long transcripts.

- **Snapshot `lastEventId` was never meaningful before today.** The server stamped it with the hub's counter while each socket renumbered events from one, so the replay cutoff on a thread switch compared two unrelated sequences. It happened to work only because a single connection since boot keeps the numbers aligned. That is fixed as a side effect of the heartbeat work, but it is worth knowing it was silently broken.

- **`session.resume` is used as a read.** `readSession` in the store resumes a session to inspect it, then resumes the active one again to undo the side effects. On the server, resume touches the last-session pointer, may activate a runtime, and now emits a state event. A read-only `session.read` request would be cleaner.

- **The web extension registry is add-only.** `registerWebExtensions` never drops an extension that is no longer served. After an unlink, the codex web module stays loaded and only disappears from the UI because `enabledExtensionIds` no longer includes it. Fine today, but any leaked module state persists until reload.

- **Project events are filtered by session id on the client.** Project status and extension events carry the session id of whoever registered the watch, and the client discards events whose session id is not the current one. If a watch was registered under a different session, its updates are dropped. I did not see it bite, but it is fragile.

- **The activity indicator can be hidden by any extension.** One `setWorkingVisible(false)` from any extension hides the titlebar and transcript indicator for the whole session. That is what removed the "Thinking" readout earlier while the composer still said streaming. A per-extension scope, or ignoring it once the session state says streaming, would avoid the contradiction.

- **`store.sessionStates` resets to idle on every connect.** The connect path sets every known session to idle before resync fixes the current one. Other sessions that are actually streaming show idle in the sidebar until their next state event.

- **The stray `word-wrap-issue.png`** you dropped at the repo root is still untracked.

None of these were in scope, so none are changed.

## assistant

The trigger isn't the panel. It's any git status change at all, and what it hits is the dev overlay, not the agent.

**The chain.** The server polls each project service every 5 seconds. An external `git add` changes the status, so the poll emits a project status event, the git badge and inspector list re-render, and the layout shifts. That shift fires the composer textarea's auto-grow resize observer, whose callback set the textarea's own height inside the observer delivery. Browsers report that as "ResizeObserver loop completed with undelivered notifications", and Vite's dev client treats it as an unhandled error and paints its full-screen error overlay over the app. That overlay is the interruption. The agent keeps running underneath it the whole time.

**Evidence.** The dev server log has 3125 of those errors going back to before this session, clustered around moments of UI activity. I checked every server path a git change can reach: the poll, the status event, the extension host, and the git extension's Pi and server sides. None touch the session, and nothing calls abort or reload. On the client, nothing subscribes to git status except the panel and the status bar item.

**The fix.** Auto-grow now re-fits only when the textarea's width changes, and does so on the next frame, since the height changes were its own doing. After the change I forced four inspector width shifts in your page and the error count did not move, where before it climbed on every layout change. The row observer I added earlier to the message list got the same treatment for safety.

If what you actually see is the run stopping rather than a red overlay, tell me what it looks like and I'll go down a different path. Nothing is committed.
