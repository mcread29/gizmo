## Snapshot

The working tree contains an uncommitted partial implementation of the requested behavior. I did not edit it.

Implemented so far:

- Removed `detect`/`detectRoots` from the server extension contract and Unity/Svelte implementations.
- New workspaces are added with no enabled integrations.
- The server now reports all loaded extensions as globally installed.
- Editing a built-in/default profile creates a `workspace:temporary` derived profile.
- Returning its values to the base removes that temporary profile.
- User-created `workspace` profiles remain supported.

## Current data flow

### Global extension installation

1. `gizmo.extensions.json` lists package specifiers.
2. `apps/agent-server/src/extensions/load-extensions.ts` imports each package’s `/server` entry.
3. `apps/agent-server/src/server.ts:18-43` registers all loaded extensions, builds:
   - `ExtensionHostService`
   - `CompositeProjectService`
   - runtime web bundles
4. `apps/agent-server/src/extensions/registry.ts:38` now returns every loaded extension with root `"."`; no workspace contents are inspected.
5. Runtime web bundles are served by `extensions.web`. However, Svelte/Git/Activity client implementations remain statically installed in `apps/app/src/lib/extensions/registry.svelte.ts`, independently of the server catalog.

### Adding a workspace

- `apps/app/src/lib/features/sessions/CommandPalette.svelte:140-146` now calls:
  ```ts
  store.addProject(selectedPath, [])
  ```
- `project.add` still requires an `integrations` array in `packages/protocol/src/index.ts:1051`.
- `ProjectCatalog.add()` in `apps/agent-server/src/projects/project-catalog.ts:120`:
  1. validates the directory;
  2. requests the extension/default-profile catalog;
  3. calls `profilesFromSelection`;
  4. writes `.gizmo/profiles.json`;
  5. writes only title/path/time to global `projects.json`.

Even with no enabled integrations, `profilesFromSelection()` currently copies the built-in default and every installed extension profile into the project file.

### Reading and saving profiles

- `.gizmo/profiles.json` is the authoritative profile file.
- `ProjectCatalog.#profiles()` reads it and `normalizeProfiles()` injects `default` if missing.
- `StoredProject.profiles` returns the complete stored array.
- `StoredProject.integrations` is a compatibility alias for the active profile’s `extensions`.
- `project.profiles.save` sends the entire `WorkspaceProfiles` object back and rewrites the file atomically.
- Only active-profile existence, known extension IDs, and roots are validated. Base references, duplicate IDs, temporary-profile invariants, and inheritance are not validated.

### Session activation

- `AgentStore.newSession()` sends only the selected active profile’s `integrations`.
- `PiAgentService` activates those extensions through `activateExtensions()`.
- Active extensions unconditionally contribute both tools and prompt fragments.
- The active profile’s `tools.mode` and `prompt.mode` are not passed to or honored by session creation.
- Skills are resolved separately from the currently active stored profile.

Resuming a thread re-resolves the workspace’s current active integrations rather than restoring a thread-specific profile snapshot.

## Important gaps in the partial implementation

### 1. Manual enablement does not gate all extension behavior

Project profiles now manually select extensions, but several capabilities remain globally active:

- `apps/agent-server/src/extensions/registry.ts:26` and `pi-agent-service.ts:798` add `defaultTools` from every installed extension. Git therefore supplies `git_status` even when Git is unchecked.
- `ExtensionHostService` receives every installed provider and does not consult project profiles. Disabled Git/Unity providers can still list and invoke project operations.
- `CompositeProjectService` similarly contains every installed project service.
- `WorkspaceInspector.svelte`, `Titlebar.svelte`, and `CommandPalette.svelte` call static contributions from every client-installed web extension without filtering `activeDomains`.
- Activity is already visible globally; checking Activity in a profile currently has no effect.
- Skill Authoring’s resources have independent skill enablement; checking that extension also has no meaningful effect.

Either gate those capabilities by the active profile, or exclude non-activatable/global-only packages from the profile checkbox list.

### 2. Some revert actions mutate the canonical profile directly

In `WorkspaceConfigurePanel.svelte`:

- normal field changes call `editableProfile()`;
- `revertTools()`, `revertPrompt()`, and `revertToBase()` mutate `editing` directly.

An extension default already differs from its `default` base, so its revert controls are visible. Invoking them can mutate the canonical extension profile instead of creating a temporary override.

All profile writes should go through one mutation helper that first resolves/creates the editable profile.

### 3. Temporary overrides are only a client convention

`workspace:temporary` is allowed by the existing generic `source: string` field. The server:

- saves temporary profiles like ordinary profiles;
- does not remove one equal to its base;
- permits several temporary profiles for the same base;
- permits missing bases;
- trusts clients to preserve canonical profiles.

The UI removes an equal override, but alternate or stale clients can violate “only while values differ.” Server-side normalization on save/read is the minimal reliable enforcement.

### 4. “Canonical” defaults are still copied snapshots

`ProjectCatalog.profilesFromSelection()` stores every extension template in `.gizmo/profiles.json`. A package update changing an extension’s default will not update existing workspaces.

If “canonical” means the current bundled extension default, storage needs a stronger change: store only user profiles and overrides, then materialize canonical profiles from the installed extension catalog on read. If it only means “the unchanged default entry already copied into this workspace,” the current v1 storage can remain.

### 5. The protocol still models detection

Although filesystem probing has been removed, the wire contract still exposes:

- `ProjectDomains`
- `project.detect`
- `detected: boolean`
- `detectProject()`
- `detectExtensions()`

The implementation reports `detected: false` for everything. This is misleading rather than genuinely removing detection.

### 6. Manual nested roots cannot be configured

All installed extensions now default to `"."`. The Configure UI displays a non-dot root but provides no root editor or folder picker. A monorepo user cannot manually set Svelte to `apps/app`, despite server support for nested roots.

### 7. Tool and prompt profile settings currently do nothing

`tools.mode` and `prompt.mode` are editable and persisted, but `createDefaultPiSession()` activates extension tools and prompts solely from `integrations`. This should be corrected as part of profile activation; otherwise temporary overrides of these values are cosmetic.

## Recommended minimal implementation

### Protocol

Replace the detection terminology with an installed catalog, for example:

```ts
interface InstalledExtensionCatalog {
  extensions: Array<{ id: string; name: string; defaultRoot: string }>;
  defaultProfiles: WorkspaceProfile[];
}
```

- Rename `project.detect` to `project.extensions.catalog` or similar.
- Remove `detected`.
- Make `project.add.integrations` optional or remove it; new workspaces begin with none.
- Bump `protocolVersion`.
- If compatibility is needed, retain `project.detect` temporarily as a deprecated alias rather than reporting fake detection results.

### Storage

For the smallest compatible change, retain version 1 and full profiles:

- Canonical entries keep `builtin:*` or `extension:*`.
- User profiles keep `workspace`.
- Temporary overrides use `workspace:temporary`, a unique ID, and `base` pointing to the canonical profile.
- On save, server normalization should:
  - reject duplicate IDs;
  - require every active/base ID to resolve;
  - permit at most one temporary override per canonical base;
  - remove a temporary override whose normalized values equal its base;
  - move `activeProfileId` back to the base when that happens;
  - leave ordinary user-created profiles unchanged.

If package-default updates must flow into existing workspaces, introduce storage v2 containing only user profiles and overrides; materialize canonical defaults at read time.

### Activation

Resolve the complete active profile on the server and use it to:

- activate only its listed extensions;
- include extension tools only when `tools.mode` allows them;
- include prompt fragments only when `prompt.mode` allows them;
- gate extension-host providers and project services;
- gate project-specific web contributions.

Move Git’s `defaultTools` behavior to normal active-extension tools, unless Git is deliberately declared as a separate always-global capability.

### UI

- Route every mutation, including all revert actions, through `editableProfile()`.
- Reuse an existing temporary override for a canonical base instead of creating `-override-2`, `-override-3`, etc.
- Add a root input/folder chooser for enabled extensions.
- Keep historical tool-result renderers loaded globally so old transcripts remain readable, even when an extension is currently disabled.
- Decide whether a saved differing override should be labeled “temporary” or “project override”; it is durable while different.

## Tests to add

Existing additions cover helper equality and one Default extension-toggle/reset path. Missing important coverage:

1. New workspace does not inspect marker files and starts with no active extension.
2. All globally installed extensions appear, including those without a profile.
3. Disabled Git/Unity contributes no tools, host descriptors, project service, tabs, commands, or status.
4. `tools.mode` and `prompt.mode` affect actual session construction.
5. Editing and reverting tools/prompt/name on an extension-provided default never mutates the canonical entry.

8. User-created profile CRUD remains unchanged.
9. Manual nested root round-trip and traversal/non-directory rejection.
10. Extension uninstall/reinstall while a stored profile references it.
11. Canonical package-default changes, according to the chosen snapshot/live-default policy.
12. Protocol rejects obsolete detection payloads after the version bump.
