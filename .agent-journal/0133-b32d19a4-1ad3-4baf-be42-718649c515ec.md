## assistant

The analysis and plan are written to `docs/extension-reload-plan.md`. Here is the short version.

**Why the server restarts today.** The dev runner starts the agent under `tsx watch`, and tsx follows imports through the junctions into `~/.pi/agent/extensions/<id>`. Any save inside a linked extension restarts the whole process and kills live threads. Production runs without watch, so the same edit never applies at all.

**Two loaders, one directory.** Pi loads each extension's `index.ts` through jiti with no module cache, and `session.reload` already re-reads it from disk. Gizmo loads the optional `gizmoExtension` export through native `import()`, which Node caches for the life of the process. The registry-update code comments on this staleness but cannot fix it. Project services are also built once at boot, and neither server extensions nor project services have a dispose hook.

**Web reload mostly works already.** The `/reload` command re-fetches bundles, and the reactive registry replaces them by id. The gaps are that only the requesting tab refreshes, the registry must be rebuilt by hand first, and old blob modules are never released.

**json-render is documented but not wired.** The host shares json-render and zod through the global module table, and the app's builder rewrites those imports. The registry ships a stale fork of that builder that only rewrites Svelte, so no registry extension could use json-render from the host, and none do. The only consumer is the built-in `display` tool with its fixed eight-component catalog. Extensions still write bespoke Svelte for every rich result.

**Registry inventory.** Eleven extensions, all linked. Four are thin shims over `packages/*`. Subagents and workflows are well over a thousand lines each on the server side. The git and unity bundles each carry their own copy of the design system and highlight.js. The svelte extension ships an empty bundle that still gets loaded. The registry also carries private copies of the protocol, extensions, design, and ui packages, which is how the builder drifted.

**The plan, in four phases:**

1. **Explicit reload, no restarts.** Ignore extension trees in tsx watch. Load Gizmo integrations through a fresh jiti instance per rescan so the whole graph re-evaluates. Add `dispose` to server extensions and project services, make the project-service registry rebuildable, and add an `extensions.reload` request that rescans, reloads idle Pi sessions, defers streaming ones until the turn settles, and broadcasts a change event so every client re-fetches bundles.
2. **Gizmo owns the web build.** Move the builder into a workspace package the server imports, build bundles on link, update, and reload, delete the registry fork, add an opt-in file watcher for dev, and release old blob modules.
3. **json-render as a real surface.** Let web extensions contribute catalogs, let the display envelope name a catalog, add a server helper for building the envelope, and share the design system through host modules to cut about 640 KB from two bundles.
4. **Registry hygiene.** Publish an SDK package, add a per-extension manifest with an API version, fold the thin shims into their extension directories, split the two oversized extensions, and move to a single enablement model.

The main risk is that jiti re-evaluation keeps old module instances alive, so the dispose hooks in phase 1 are a prerequisite for the reload, not a follow-up.

## assistant

In the registry repo, four extensions don't contain their real code. Their `extensions/<id>/` directory holds only a tiny entry file that re-exports from a separate workspace package under `packages/`.

Concretely, in `~/.gizmo/registries/gizmo-registry`:

- `extensions/git/pi-extension.ts` is 23 lines. It imports and re-exports from `packages/git/src/server`, and its web entry re-exports `packages/git/src/web/index`.
- `extensions/unity/pi-extension.ts` is 43 lines. The tools, docs indexer, and `gizmoExtension` all live in `packages/unity/src/server/`, and the web bundle comes from `packages/unity/src/web/`.
- `extensions/activity/pi-extension.ts` is 9 lines over `packages/activity`.
- `extensions/svelte/pi-extension.ts` is 12 lines over `packages/svelte`.

So the "extension" the registry lists, links, and builds is a shim. The logic sits two directories up, reached by relative imports like `../../packages/unity/src/server/index.ts`. That works because the junction link into `~/.pi/agent/extensions/<id>` resolves relative paths back into the registry clone.

Why it matters for the plan:

- **An extension is not one tree.** Linking, watching, building, and reloading all have to reason about `extensions/<id>` plus whichever `packages/*` it reaches into. A file watcher scoped to the linked directory would miss most of the real source.
- **Inconsistent with the other seven.** Codex, ollama, subagents, workflows, ask-user, search-and-scrape, and skill-authoring keep everything under their own directory. Two layouts means two mental models for the same registry.
- **The split exists for history, not need.** Those four packages are the ones that were originally inside the Gizmo repo before extensions moved out. The `packages/` layout is a leftover of that move.

The phase 4 recommendation is to move each package's source under its extension directory so every extension is self-contained, which also makes the phase 2 watcher and per-extension build trivial.
