## The catch: the dev server watches itself

`scripts/dev-server.ts:79` spells it out:

> the agent runs under `tsx watch`, so edits to the server or to any workspace package it imports (protocol, extensions) restart it in place

So an agent working on `apps/agent-server/**`, `packages/protocol`, or `packages/extensions` **tears down its own runtime the moment it saves a file**. Mid-turn, that kills the in-flight response — and `session-transcript.ts` notes the transcript file only gains an assistant message once it *completes*, so that turn's output is lost, not just interrupted.

Editing `apps/app` or `packages/ui` is fine. Vite HMR handles those and the agent server never restarts. So frontend work self-hosts cleanly today; backend work is where it bites.

## What survives a restart

Quite a lot, because the persistence model is file-first:

- Session JSONL is append-only and Pi never rotates or deletes it.
- `delete` now archives rather than unlinks.
- `SessionRuntimePool` treats live runtimes as a cache; `resumeSession` rehydrates from the file, so reopening the session in the UI picks it back up.
- The journal extension hooks `session_shutdown`, which fires with `reason: "reload"` on a watch restart — so the tail gets journaled even when the turn itself is lost.

You lose the in-flight turn, not the thread.

## The setup I'd actually use

Two instances: develop *in* a stable one, develop *on* the watched one.

```bash

  pnpm --filter @gizmo/agent-server start

# iterating — the usual watched pair on 8787
pnpm dev:server:start
```

`start` (`package.json`) is plain `tsx src/server.ts` with no watcher, which is the whole trick — it keeps running the code as of launch until you deliberately restart it. `GIZMO_DATA_DIR` keeps sessions, projects, and registry state separate so experiments can't corrupt the sessions you're working in.

One wrinkle: the app hardcodes `ws://127.0.0.1:8787` (`WebSocketAgentClient.ts:43`, and the Vite proxy target). Pointing the UI at 8788 needs a small change or an env-driven URL. Simplest today is to drive the stable instance from the Claude Code CLI or a second Vite with a patched proxy.

## One behavioral difference to know

`pnpm dev:server` sets `GIZMO_PI_WEB=1` (`dev-server.ts:76`), but plain `pnpm dev` does not. In pi-web mode `agentDir` becomes Pi's own `~/.pi/agent` instead of `~/.gizmo`, the Gizmo model runtime is skipped, and project-trust resolution kicks in. So the managed dev server and the raw dev script are not the same environment — worth pinning deliberately rather than discovering later.

## The fix

`session-transcript.ts:62` created every tool call as `status: 'running'` and relied on a matching `toolResult` to settle it. When a turn aborts mid-stream that result never arrives — and since this view is **rebuilt from the session file on every load**, the call reads as running forever. Reloading wouldn't have helped, and neither would restarting. I was wrong about that earlier.

Now, after the branch is read, any unsettled call gets resolved:

- Only the **newest assistant message** can still have tools in flight, so anything older with no result is finished.
- Even the newest can't be running if the provider reported `stopReason: "aborted"` or `"error"`.
- Everything else becomes `error` / **"Interrupted"**.

Two cases it deliberately preserves: a genuinely executing tool on the latest turn stays `running` (tools execute *after* their message is written), and sibling calls in a batch stay running when only one has returned.

## What actually happened

I misread the abort as yours. It wasn't. Look at the timing across **both** sessions:


Two independent sessions, same provider, 53 seconds apart, both with zero token usage. That's a provider or connection drop, not you. The Slapdash run died on its own while you were mid-thought.

Then you steered. `_queueSteer` (`agent-session.js:1046`) does two things: pushes onto `_steeringMessages`, and injects the message into the running agent's stream. Steering is delivered *after the current turn finishes its tool calls, before the next LLM call* — but there was no next LLM call, because the run had just been aborted. So `path` got persisted into the transcript as part of the dying run's message list and **never reached the model**.

That's why the thread shows nothing: not a rendering bug, an undelivered message. Your instinct was right.

## The fix

Pi already provides the exact primitive, and its doc comment names this case:

```
/**
 * Clear all queued messages and return them.
 * Useful for restoring to editor when user aborts.
 */
clearQueue(): { steering: string[]; followUp: string[] }
```

**gizmo never calls it.** `SessionOperations.abort()` (`session-operations.ts:188`) does `cancelConfirmations` → `cancelDialogs` → `session.abort()`, and stops. Nothing recovers the queue.

Two parts, and the second matters more given it wasn't a user abort:

1. **Recover the queue when a run ends with anything pending** — not just on user abort, since here the provider killed it. Hook run settlement, and if `pendingMessageCount > 0`, `clearQueue()` and hand the text back to the composer as a draft. The Composer already has this pattern for rejected sends (`Composer.svelte:158` restores the draft on `error.kind === 'prompt'`), so there's an established shape to slot into.

2. **Render the aborted turn.** An assistant message with `stopReason: 'aborted'` currently displays as nothing. The user should see "response interrupted" rather than silence — same class of problem as the stuck tool call I just fixed, and the same `stopReason` signal drives it.

There's also a UI hazard worth noting separately: while streaming, **Stop** (red square) and **Steer** (arrow) sit immediately adjacent in `ComposerToolbar.svelte`. That's not what bit you here, but it's a misclick waiting to happen, and the consequence — a silently discarded turn — is severe enough to deserve separation or a confirm.

Want me to implement the queue recovery? Part 1 is the one that would have saved your message. Part 2 is a display change and needs a call on how you want an interrupted turn to read in the transcript.
