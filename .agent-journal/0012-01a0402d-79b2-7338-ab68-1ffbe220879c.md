### Profile/runtime gaps

Several current controls are not enforced by the backend:

## Recommended model

I would interpret “enabled per project” as a workspace-level allowlist. Profiles may activate/configure only extensions enabled for that workspace.

Persist a versioned project configuration such as:

```ts
{
  version: 2,
  enabledExtensions: [{ id: 'svelte', root: 'apps/app' }],
  activeProfileId: 'default',
  profileOverrides: [
    // Patches for canonical defaults; omitted when empty
  ],
  profiles: [
    // Normal user-created profiles; always persisted
  ]
}
```

Key rules:

1. **Canonical profiles are not written to the workspace.**
   - Core contributes `default`.
   - Each globally installed extension may contribute a canonical default.
2. **Editing a canonical profile creates a temporary draft override.**
   - Save persists only its patch.
   - Reverting the final difference removes the override.
   - An unchanged profile therefore resolves directly from the current canonical definition.
3. **New profiles are normal project-owned records.**
   - They remain persisted even if their effective values happen to match a default.
   - They can be renamed, activated, duplicated, and deleted normally.
4. **Extension roots belong to workspace extension enablement**, not duplicated across every profile.
5. **Profiles reference enabled extension IDs**, and the server joins them to workspace roots when composing a session.
6. Disabling an extension should be blocked while a profile references it, with the dependent profile names shown. This avoids silently destroying profile configuration.
