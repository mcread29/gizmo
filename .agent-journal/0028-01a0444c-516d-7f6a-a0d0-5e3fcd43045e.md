## Building the pi extensions' UI

```
pi-extensions/
  ask-user/
    pi-extension.ts          ← backend tool (embedded → seeded into the data dir)
    src/web/index.ts         ← its UI entry (optional per extension)
    src/web/AskUserToolResult.svelte
  ask-user.web.js            ← built output (5 KB), travels with the extension
```

- **`pnpm pi-extensions:build`** (bun) — loops every `pi-extensions/*/src/web/index.ts` through the app's existing web-extension bundler (`buildWebExtension`, the same one Unity uses — Svelte compiled, Svelte runtime shared with the host) and emits a sibling `<name>.web.js`. Nothing is packaged into the compiled server build; the outputs are plain files that install into a Pi agent directory right next to the extension.
- Gizmo's runtime bundle loader (`extensions.web` → `registerWebExtensions`) picks up sibling bundles paired by file stem — that discovery wiring is the remaining server piece for third-party agent-dir extensions; the shipped one is verified working through the static path today.

## What this changed structurally

- `@gizmo/ask-user` (the package from the last step) is dissolved — per your rule, the UI now lives *with the extension*, not in a package the app statically bundles. The app has **zero** ask_user knowledge again: the tool comes from pi loading the seeded extension, the label and result rendering come from the runtime-loaded `.web.js`, and the question card is the generic bridge renderer.
- For your **globally installed subagents/workflows**: when you're ready, each gets `src/web/index.ts` in its agent-dir directory (or vendored here) with `labels`/`resultFor`/`inspectorTabs` keyed by their tool names — `pnpm pi-extensions:build` produces their `.web.js` files, and no UI ever exists apart from its extension.
