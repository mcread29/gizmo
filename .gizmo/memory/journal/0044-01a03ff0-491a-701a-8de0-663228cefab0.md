## Recommended wire protocol

Bump `protocolVersion` to `20`.

Add exported TypeBox schemas/types in `packages/protocol/src/index.ts`:

```ts
ExtensionUIRequest
ExtensionUIResponse
ExtensionUICancellationReason
```

Use a session-runtime identity in addition to the request ID:

```ts
runtimeId: string
uiRequestId: string
```

`runtimeId` is necessary because reload and idle reconstruction can create a new extension runtime for the same `sessionId`.

### Client-to-server request

Add `extension.ui.respond` to `agentRequestSchema`:

```ts
{
  type: "extension.ui.respond",
  sessionId,
  runtimeId,
  uiRequestId,
  response:
    | { kind: "value", value: string }
    | { kind: "confirmed", confirmed: boolean }
    | { kind: "cancelled" }
}
```

The service must validate response kind against the pending method:

- `select`, `input`, `editor` accept `value` or `cancelled`
- `confirm` accepts `confirmed` or `cancelled`
- `select` should additionally reject a value not present in the original options

### Server-to-client events

Add these to `agentEventSchema`.

#### `extension.ui.requested`

```ts
{
  type: "extension.ui.requested",
  runtimeId,
  uiRequestId,
  request: ...
}
```

Request union:

- `{ method: "select", title, options, timeout? }`
- `{ method: "confirm", title, message, timeout? }`
- `{ method: "input", title, placeholder?, timeout? }`
- `{ method: "editor", title, prefill? }`
- `{ method: "notify", message, notificationType }`
- `{ method: "setStatus", key, text: string | null }`
- `{ method: "setWidget", key, lines: string[] | null, placement }`

- `{ method: "setEditorText", text }`

Use explicit `null` for status/widget clearing rather than relying on `undefined`, which disappears during JSON serialization.

#### `extension.ui.cancelled`

Dismiss one outstanding dialog when the server resolves it without a browser response:

```ts
{
  type: "extension.ui.cancelled",
  runtimeId,
  uiRequestId,
  reason: "timeout" | "signal" | "abort"
}
```

#### `extension.ui.runtime.cleared`

Clear all dialogs and persistent contributions belonging to a stale runtime:

```ts
{
  type: "extension.ui.runtime.cleared",
  runtimeId,
  reason: "reload" | "evicted" | "deleted" | "disposed"
}
```

Notifications may remain as ordinary toast history, but statuses, widgets, titles and dialogs must be removed.

## Recommended service/runtime implementation

### New runtime abstraction

Add:

`apps/agent-server/src/sessions/pi-extension-ui-runtime.ts`

It should own:

- one `runtimeId`
- an `ExtensionUIContext`
- pending dialog map
- timeout handles
- abort listeners
- accepting/suspended/disposed state
- event callback into `PiAgentService`

Suggested API:

```ts
context: ExtensionUIContext
hasPendingDialogs: boolean
resolve(uiRequestId, response): void
cancelDialogs(reason): void
suspend(reason): void
startRuntime(): void
dispose(reason): void
```

Dialog defaults:

- select/input/editor → `undefined`
- confirm → `false`

For `select`, `confirm`, and `input`:

1. Return the safe default immediately if `opts.signal?.aborted`.
2. Allocate `uiRequestId`.
3. Register abort and timeout cleanup.
4. Emit `extension.ui.requested`.
5. Resolve exactly once on response, timeout, signal, abort, or runtime cleanup.

Fire-and-forget methods simply emit an event tagged with the current runtime.

The full required `ExtensionUIContext` must also provide safe degradation:

- `custom()` → `undefined`
- component-factory `setWidget` → ignore
- footer/header/custom editor/autocomplete/working methods → no-op initially
- `onTerminalInput()` → no-op unsubscribe
- `getEditorText()` → `""`
- `pasteToEditor()` → delegate to `setEditorText()`
- theme operations → explicit unsupported results
- tool expansion reads → `false`

### Bind after service activation

The current binding occurs inside `createDefaultPiSession`, before `#activate()`. That creates a serious ordering problem: a `session_start` handler can emit a widget or block on `select()` before the service has emitted `session.created`.

Recommended sequence:

1. Factory creates the Pi session but does not bind extensions.
2. `PiAgentService` installs the session in `#sessions`.
3. Emit `session.created` and initial state.
4. Call:

```ts
session.bindExtensions({
  uiContext: extensionUI.context,
  mode: 'rpc',
  onError: ...
});
```

5. Complete `session.create`/`session.resume`.

This also allows a browser response to reach an already-registered runtime while `bindExtensions()` is awaiting a `session_start` dialog.

If minimal refactoring keeps binding inside the factory, the frontend must support extension UI events for a session before `session.created` and before the create response. That is functional but fragile.

### Reload lifecycle

`AgentSession.reload()` retains and reapplies the same UI context. The bridge therefore must roll its own `runtimeId`.

In `reloadSession()`:

1. `extensionUI.suspend("reload")`
   - cancel pending dialogs
   - emit runtime cleanup
   - reject/no-op new calls made by the old runner during shutdown
2. Call:

```ts
session.reload({
  beforeSessionStart: () => extensionUI.startRuntime()
});
```

Pi invokes this callback after the old runner is shut down and the new runner is built, but before the new `session_start`. New startup statuses/widgets therefore belong to the new runtime.

### Other lifecycle paths

- `abort()`:
  - cancel dialogs with safe defaults
  - do **not** clear persistent status/widgets
  - then call Pi abort
- `deleteSession()`:
  - dispose UI runtime before session disposal
- `#evict()`:
  - dispose UI runtime and emit runtime cleanup
- `dispose()`:
  - resolve every pending dialog before clearing maps
- creation failure:
  - dispose the bridge and remove any partially activated session
- `abortStreamingSessions()`:
  - cancel dialogs before or alongside direct Pi abort

Idle eviction should not evict a runtime with a pending dialog, or it should deliberately cancel it first. Silently disposing a promise that an extension is awaiting would leak the extension call.

## Important pitfalls

1. **No extension attribution exists.** Pi supplies one shared UI context and does not pass extension path/source metadata into UI calls. Per-extension key isolation and owner labels require a Pi SDK enhancement; Gizmo cannot infer ownership reliably.
2. **`mode: "json"` is wrong for the bridge.** Use `"rpc"` with a real context.
3. **`bindExtensions()` fires lifecycle events immediately.** Binding order matters.
4. **Reload reuses the context object.** A separate `runtimeId` generation is mandatory.
5. **Pi `dispose()` does not emit `session_shutdown`.** Gizmo must clean up UI independently on eviction/delete/disconnect.
6. **`editor()` cannot receive timeout/signal in 0.84.2.** It can only be cancelled by browser response or host/runtime cleanup.
7. **Widget factories cannot be transported.** Only string arrays should emit events.
8. **Composer writes must be session-scoped.** An inactive session’s `setEditorText` event must not overwrite the visible thread’s draft.
9. **Theme-styled strings may contain ANSI escapes.** Browser rendering should strip or safely interpret them rather than display raw escape sequences.
10. **Do not reuse Unity’s confirmation map.** Pi UI needs method-aware responses, timeout/signal cleanup, runtime generations, and multiple simultaneous requests.
