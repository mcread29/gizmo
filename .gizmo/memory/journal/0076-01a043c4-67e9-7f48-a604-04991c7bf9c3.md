They load through **two separate pipelines** that converge at session creation in `createDefaultPiSession` (`apps/agent-server/src/sessions/pi-agent-service.ts:813`). They never mix catalogs — each has its own discovery, opt-in, and capability surface.

## Gizmo extensions (`GizmoServerExtension`)

**1. Discovery — server startup, once.** `server.ts:19-28` reads `gizmo.extensions.json` (overridable via `GIZMO_EXTENSIONS_CONFIG`) and calls `loadServerExtensions()` (`extensions/load-extensions.ts`), which dynamic-`import()`s each specifier's `<pkg>/server` subpath and expects a `gizmoExtension` export. It validates the `id` (tame charset — ids become map keys and path components) and resolves `packageRoot` from the import. Any failure logs a warning and skips — startup never crashes on a bad extension. The result goes into `registerExtensions()` (`extensions/registry.ts`) as the global catalog.

**2. Activation — per session, profile-driven.** Loading ≠ enabling. When a session is created, the workspace's active profile supplies `integrations: [{id, root}]`; `activateExtensions()` (`registry.ts:44`) looks each id up in the catalog, validates the integration root is inside the workspace, and assembles:
- `systemPrompt` — core prompt + each extension's fragment + its integration root
- `tools` — `extension.createTools({workspacePath: integrationRoot})`, only included when the profile's tool mode is `default-plus-extension` (`extensionTools` flag)

**3. Injection into the Pi session.** `customTools = [...activeDomains.tools, runScriptTool]` (`pi-agent-service.ts:847`) is passed to `createAgentSessionFromServices()`. In normal Gizmo mode the tool allowlist is `['read', 'edit', 'write', ...customTools, ...piExtensionToolNames]`; in Pi Web mode there's no allowlist.

**4. Companion surfaces.** `packageRoot` also feeds `extensionResourceRoots()` → the extension's shipped `skills/`+`prompts/` join `additionalSkillPaths`/`additionalPromptTemplatePaths` (Pi's own package convention). `createProjectService()` factories are composed into a `CompositeProjectService` at startup (`server.ts:33-40`). On the client, `web-bundles.ts` reads each `dist/web.js` and ships it over the existing agent WebSocket; the browser blob-imports it, validates every optional field individually, and requires the bundle's `id` to match what the server called it.

## Pi extensions

**1. Ambient discovery is off.** `resourceLoaderOptions` sets `noExtensions: true` — Pi's normal scan of `~/.pi/agent/extensions` is not what loads them.

**2. Gizmo curates instead.** `enabledPiExtensionPaths()` (`resources/pi-global-resources.ts:30`) lists `~/.pi/agent/extensions` (enabled) vs `extensions-disabled/` — Gizmo's resource catalog enables/disables by *moving files between those directories* (`setPiExtensionEnabled`, a `rename`). Enabled paths are passed as `additionalExtensionPaths`, so Pi's resource loader loads exactly those, through Pi's own machinery (trust, tools, hooks, commands all work).

**3. Binding.** After session creation: `session.bindExtensions({mode: 'json', uiContext: callbacks.extensionUi.context})` (`pi-agent-service.ts:~960`). Headless `json` mode — TUI-specific contributions (themes, footers, custom components) have no renderer and degrade, but everything else runs. Their tool names are collected via `services.resourceLoader.getExtensions()` and joined to the allowlist (`piExtensionToolNames`, `pi-agent-service.ts:926`); their commands surface in the composer's `/` palette via `session.extensionRunner.getRegisteredCommands()` (source: `'extension'`). UI requests (dialogs, widgets, statuses, titles, editor commands) route through `PiExtensionUiRuntime`, which translates them into Gizmo's native web UI — that's the bridge plan in `docs/pi-extension-ui-bridge-plan.md`.
