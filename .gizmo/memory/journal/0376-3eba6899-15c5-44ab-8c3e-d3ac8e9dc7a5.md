Yes — and the architecture actually supports it well. But there's one structural catch worth understanding before you rely on it.

## The catch: the dev server watches itself

`scripts/dev-server.ts:79` spells it out:

> the agent runs under `tsx watch`, so edits to the server or to any workspace package it imports (protocol, extensions) restart it in place

So an agent working on `apps/agent-server/**`, `packages/protocol`, or `packages/extensions` **tears down its own runtime the moment it saves a file**. Mid-turn, that kills the in-flight response — and `session-transcript.ts` notes the transcript file only gains an assistant message once it *completes*, so that turn's output is lost, not just interrupted.

Editing `apps/app` or `packages/ui` is fine. Vite HMR handles those and the agent server never restarts. So frontend work self-hosts cleanly today; backend work is where it bites.

## What survives a restart

Quite a lot, because the persistence model is file-first:

- Session JSONL is append-only and Pi never rotates or deletes it.
- `delete` now archives rather than unlinks.
- `SessionRuntimePool` treats live runtimes as a cache; `resumeSession` rehydrates from the file, so reopening the session in the UI picks it back up.
- The journal extension hooks `session_shutdown`, which fires with `reason: "reload"` on a watch restart — so the tail gets journaled even when the turn itself is lost.

You lose the in-flight turn, not the thread.

## The setup I'd actually use

Two instances: develop *in* a stable one, develop *on* the watched one.

```bash
# stable — the one you work in. `start` is tsx WITHOUT watch,
# so editing source never restarts it.
GIZMO_PORT=8788 GIZMO_DATA_DIR=~/.gizmo-stable \
  pnpm --filter @gizmo/agent-server start

# iterating — the usual watched pair on 8787
pnpm dev:server:start
```

`start` (`package.json`) is plain `tsx src/server.ts` with no watcher, which is the whole trick — it keeps running the code as of launch until you deliberately restart it. `GIZMO_DATA_DIR` keeps sessions, projects, and registry state separate so experiments can't corrupt the sessions you're working in.

One wrinkle: the app hardcodes `ws://127.0.0.1:8787` (`WebSocketAgentClient.ts:43`, and the Vite proxy target). Pointing the UI at 8788 needs a small change or an env-driven URL. Simplest today is to drive the stable instance from the Claude Code CLI or a second Vite with a patched proxy.

## One behavioral difference to know

`pnpm dev:server` sets `GIZMO_PI_WEB=1` (`dev-server.ts:76`), but plain `pnpm dev` does not. In pi-web mode `agentDir` becomes Pi's own `~/.pi/agent` instead of `~/.gizmo`, the Gizmo model runtime is skipped, and project-trust resolution kicks in. So the managed dev server and the raw dev script are not the same environment — worth pinning deliberately rather than discovering later.

## Where it'd pay off

Self-hosting is what would exercise the memory journal properly: every session on gizmo-in-gizmo writes segments into `.gizmo/memory/journal/`, and the compaction and `session_before_tree` hooks only really get tested by sustained real use. Right now that's all validated against backfilled history, not live capture.

## A testability gap worth closing

The `turn_end` threshold is hardcoded at 96KB (`journal-recorder.ts`) and the extension constructs `new JournalRecorder(new JournalStore(ctx.cwd))` with no options — so there's no way to tune it without editing source. That makes the threshold path slow to exercise deliberately and gives you no way to make segments finer while evaluating quality.

I'd add a `GIZMO_MEMORY_JOURNAL_THRESHOLD` env override. Small, and it makes the whole thing testable in minutes instead of hours.
