The same pattern applies, with one decision up front. Here's how I'd do it:

## The shape

Two paired packages — `packages/subagents` and `packages/workflows` — contributing **web presentation** keyed by tool names, exactly like ask_user does:

**Subagents (`packages/subagents`)**:
- `labels`/`iconFor` — `subagent_spawn` → "Spawn subagent", `subagent_wait`, `subagent_list`, etc.
- **`resultFor`** — native rendering on the tool calls: a spawn shows the subagent's id/task/status; a wait shows its transcript tail or result; a list shows the roster.
- **`inspectorTabs`** — a "Subagents" tab in the workspace inspector that derives live state from `InspectorTabContext.toolActivity` (spawn → running, wait → completed), no RPC server needed.
- possibly `parametersFor` to trim bulky task prompts from the generic call line.

**Workflows (`packages/workflows`)**:
- Same shape: labels, `resultFor` for run progress/outcome, and a "Workflows" inspector tab listing runs and their steps from tool activity.

**What stays generic**: the interactive parts you already have — `ask_user`-style questions, working indicators, widgets — render through the bridge for free. Subagent tools that need to ask mid-run would get the chat card automatically.

## The one design fork

The tools live in your **globally installed** agent-dir extensions, and web presentation is keyed by *tool name*, which works regardless of where the tool comes from. So the web packages can ship in Gizmo while the Pi extensions stay personal — the UI simply activates whenever those tools appear in a session. The alternative is full ask-user-style vendoring (Pi extension + UI in one package, seeded, shipping to every install).

The thing that *doesn't* work yet is **attribution**: the bridge's UI requests carry a session/runtime id but not *which extension* raised them, and pi doesn't report tool ownership — that's the "extension attribution in Pi" phase in the bridge plan. Until then, tool-name keying is the contract, and per-project `piExtensions` disables won't automatically hide a subagents tab (the tab derives from tool activity, which only exists if the tools ran).

Got it — that's a strict and good rule: **UI never ships without its extension.** And it points at the one thing Gizmo's web-extension system can't do today: a *globally installed Pi extension* has no way to carry UI. Unity's UI travels because it's a `GizmoServerExtension` with a `packageRoot`; your agent-dir extensions are just code files pi loads. So here's the design I'd build:

## The mechanism: sibling web bundles

A Pi extension may ship its UI **next to itself** in the agent directory:

```
~/.pi/agent/extensions/
  ask-user.ts          ← backend (tool)
  ask-user.web.js      ← its UI bundle (pre-built browser JS)
  subagents.ts
  subagents.web.js
  workflows.ts
  workflows.web.js
```

Pairing key = the extension file's stem. Gizmo already loads runtime web bundles (`extensions.web` → `registerWebExtensions`) — Unity proves the browser side end-to-end. The only new machinery is **server-side discovery**: when Gizmo collects Pi extension paths for a session, it also checks each for a sibling `.web.js` and serves it over `extensions.web` with the stem as the id, deduped against Gizmo extensions and builtins.

## What that gives each audience

- **Your global subagents/workflows**: their UI lives beside them, versioned wherever they're versioned. Gizmo renders their tool calls, adds their inspector tabs, and — once pi reports extension attribution — their per-workspace enable/disable in Configure gates both tools and UI together. They ship wherever the extensions ship.
- **ask_user**: its web extension moves out of the app's static builtins into a seeded `ask-user.web.js` beside `ask-user.ts` — re-joining the pair, per your rule. (The chat question card itself stays shell-generic: it renders *any* extension's bridge requests, like the composer renders any extension's text.)
- **Authoring story for anyone**: "put a `.web.js` next to your extension and Gizmo gets UI." The bundle declares `id`, `labels`, `resultFor`, `inspectorTabs`, etc. — the same `GizmoWebExtension` contract, no Gizmo fork required.

## Build steps, in order

1. **Server discovery** — extend bundle collection to pi extension paths (agent-dir + seeded), id = stem, deduped.
2. **Seed pairs** — the seeding list gains per-extension web files (embedded like the Pi source).
3. **Move ask-user's UI** — `packages/ask-user`'s web part becomes the authored bundle built to `ask-user.web.js`; drop the static builtin; `packages/ask-user` dissolves (or stays as the build source for the pair).
4. **Subagents/workflows UI** — authored against the same contract: result renderers + inspector tabs deriving state from tool activity.

One open piece sits in pi itself: the runner knows each extension's path but UI requests don't carry extension attribution — fine for bundle delivery, needed later if you want per-extension request rendering or per-extension gating of UI requests.
