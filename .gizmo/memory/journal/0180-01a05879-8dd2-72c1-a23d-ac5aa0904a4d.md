## Executive summary

Highest-value refactors:

1. **Split `AgentStore` and its fake client by capability.**
   - `apps/app/src/lib/agent-client/AgentStore.svelte.ts` is a 1,335-line façade covering connection, sessions, projects, resources, extensions, Git, models, tool policy, registry, attachments, and event replay.

5. **Move tests out of production source and split the two test monoliths before implementation changes.**
   - `App.test.ts` is 999 LOC with 33 scenarios.

# Main findings

## 1. `AgentStore` is the primary architectural bottleneck

### Mixed responsibilities

`apps/app/src/lib/agent-client/AgentStore.svelte.ts` currently owns:

- WebSocket connection and reconnect backoff
- Subscription lifecycle
- Session catalog, creation, switching, deletion, branching and renaming
- Transcript state and replay buffering
- Model/thinking selection
- Composer commands
- Project discovery, selection, status and opening
- Runtime web-extension installation
- Project-extension activation/invocation
- Resources, skills and Pi/Gizmo extension configuration
- Registry operations
- Tool policy
- Git status and commits
- Attachments and confirmations
- Error projection for every domain

The component tree consequently depends on one very broad mutable object. `AgentClient.ts` mirrors this with a 40+ method interface.

### Recommended boundary

Keep `AgentStore` temporarily as a compatibility façade, but delegate to reactive capability stores:

```text
apps/app/src/lib/agent-client/
  AgentStore.svelte.ts
  connection/
    ConnectionStore.svelte.ts
  sessions/
    SessionStore.svelte.ts
    session-selection.ts
    replay-buffer.ts
  workspaces/
    WorkspaceStore.svelte.ts
  resources/
    ResourceStore.svelte.ts
    ToolPolicyStore.svelte.ts
    RegistryStore.svelte.ts
  extensions/
    ProjectExtensionStore.svelte.ts
  git/
    GitStore.svelte.ts
```

Split `AgentClient` into capability interfaces such as `SessionClient`, `WorkspaceClient`, `ResourceClient`, and `ExtensionClient`, then compose them into the public `AgentClient`.

### Risks

- `switchSession` has important stale-request and event-replay guarantees.
- Workspace and session selection must continue changing atomically.
- Deeply reactive arrays/objects currently depend on Svelte proxy behavior.
- `agent-event-reducer.ts` mutates an `AgentEventState` structural interface; preserve this as a pure, independently tested boundary.
- Do not expose partially migrated child stores directly until their lifecycle and error semantics are stable.

## 2. Transport and fake-client files should follow the same capability split

### `WebSocketAgentClient.ts`

`apps/app/src/lib/agent-client/WebSocketAgentClient.ts` combines:

- Socket lifecycle and pending-request correlation
- Every protocol request wrapper
- Response parsing
- Event forwarding and disconnect behavior

Extract the socket/request engine first:

```text
apps/app/src/lib/agent-client/websocket/

  request.ts
  sessions.ts
  projects.ts
```

`apps/app/src/lib/agent-client/FakeAgentClient.ts` combines:

- Fake server state
- Scripted streaming demo behavior
- Mutable project/resource fixtures
- Session/tree behavior

- Extension UI events

Suggested structure:


Important: `fakeProjects` and several fixtures are module-level mutable values. A project added or removed by one fake-client instance can leak into later instances/tests. Convert fixtures to per-instance factories before increasing parallel test execution.

No scoped source imports `@gizmo/design/components`, making the three Svelte components in `packages/design` effectively orphaned.

### Hidden dependency

`packages/ui` renders `data-ui` attributes whose styling lives in `packages/design/src/components.css`, but `packages/ui/package.json` does not depend on `@gizmo/design`.

`apps/app/src/main.ts` works around CSS packaging with:


That bypasses package exports and couples the application to the repository layout.

### Recommended ownership

- **`packages/design`**: tokens, themes, focus rules, primitive CSS only.
- **`packages/ui`**: reusable Svelte components and presentation utilities.
- **`apps/app`**: product-specific composition such as `BrandMark` and settings-specific fields.

Candidates to move from app to `packages/ui/src`:

- `apps/app/src/lib/components/ConfirmDialog.svelte`

- `apps/app/src/lib/components/ScrollPanel.svelte`

## 5. CSS boundaries and duplication

### Large mixed files

- `settings.css` mixes settings shell, generic resource lists, skills, workspace configuration, and apparent old profile UI.
- `dialogs.css` mixes command palette, folder picker, onboarding, managed-project, and workspace-card styles.
- `shell.css` mixes app grid, titlebar, responsive panels, and the entire session tree screen.
- `composer.css` includes both the regular composer and Pi extension question UI.
- `inspector.css` includes inspector shell, tabs, Unity/activity-specific surfaces, and possible extension contracts.

### Cross-file selector overlap

Notable global collisions:

- `[data-ui='button']` customized in seven app stylesheets plus `packages/design/src/components.css`
- tabs customized in `components.css`, `inspector.css`, `changes.css`, and `workspace-dashboard.css`
- select styles repeated in `components.css`, `settings.css`, and `composer.css`
- skeleton styles spread across four app stylesheets
- inspector, conversation, sidebar, integration list, and diff selectors cross ownership boundaries

These are sometimes intentional contextual overrides, but the import-order dependency is fragile.

### Apparently unused selectors

Examples include:

- `settings.css`: `config-profilebar*`, `config-lock-*`, `profile-id`
- `dialogs.css`: `managed-project*`, `project-manager*`, many `workspace-card*` selectors
- `inspector.css`: `activity-*`, `unity-panel`, `unity-subpanel`
- `changes.css`: most `change-*` and `git-*`
- `diagnostics.css`: `test-*` and `compiler-*`
- `tool-call.css`: `script-*`, `tool-command-list`, `tool-metrics`

They do not appear in current static app/package markup. However, runtime web extensions can contribute arbitrary Svelte components, so classify these selectors as one of:

1. current app styles,
2. documented host extension CSS contract,
3. extension-owned styles,
4. dead code.

Do not delete them before that classification. Prefer extension-owned CSS bundled alongside the extension instead of undocumented host selectors.

# Svelte 5 assessment

## Good current practices

- Runes-based state and props are already used throughout.
- Event attributes use modern `onclick`/`onchange` syntax.
- Snippets are used instead of slots.
- Most meaningful lists are keyed.
- `$state.raw` is used for several replacement-only catalogs.
- `<svelte:window>` is already used for global keyboard handling.
- Message rendering documents its sanitized/escaped `{@html}` boundaries.

## Refactor targets

The Svelte autofixer found no compile failures, but highlighted:

- Unkeyed each blocks:
  - `apps/app/src/lib/components/Menu.svelte`
  - both each blocks in `apps/app/src/lib/components/Tabs.svelte`
  - orphaned `packages/design/src/SelectField.svelte`
- Mutable `Set` concern:
  - `apps/app/src/lib/features/tree/SessionTreeScreen.svelte`
- Legacy actions that should be considered for `{@attach}`:
  - `Composer.svelte` — `autoGrow`
  - `MessageList.svelte` — `measure`
  - `MarkdownContent.svelte` — delegated copy handler
- Extensive state assignment inside effects:
  - `App.svelte`
  - `WorkspaceConfigurePanel.svelte`
  - `CommandPalette.svelte`
  - `MessageList.svelte`
  - `Conversation.svelte`
  - `MarkdownContent.svelte`
  - `Tabs.svelte`
  - several smaller components

Some effects are valid external synchronization—virtualizer configuration, debounced requests, DOM/title/theme updates—but state-machine transitions should move into event handlers or focused controllers. Pure computations should become `$derived`.

The two `{@html}` uses are currently guarded:

- Markdown is sanitized with DOMPurify in `markdown.ts`.
- Highlight output comes from highlight.js, which escapes source.

Keep explicit regression tests around both trust boundaries.

Also replace `Component<any>` in:

- `apps/app/src/lib/extensions/types.ts`
- `apps/app/src/lib/features/settings/SettingsNav.svelte`

with typed component prop contracts where practical.
