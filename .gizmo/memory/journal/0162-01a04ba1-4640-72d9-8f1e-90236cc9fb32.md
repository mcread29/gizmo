## Root cause

`/compact` decides there's "nothing to compact" using a **chars/4 character estimate of message content only** (`findCutPoint` in `dist/core/compaction/compaction.js`). It walks backward from the newest message accumulating estimated tokens until it reaches `keepRecentTokens` (yours is 20,000). If the *entire session* estimates under that, it keeps everything → `messagesToSummarize` is empty → `"Nothing to compact (session too small)"`.

The problem: that estimate **excludes the system prompt and all tool schemas**, and chars/4 undercounts structured content. Your failing session is a perfect example:

| measure | tokens |
|---|---|
| real context (provider-reported usage) | **28,980** |
| pi's chars/4 estimate of all messages | **13,050** |
| `keepRecentTokens` threshold | 20,000 |

So the context is ~29k tokens deep, but pi thinks it's 13k → "session too small". It also auto-compacts using `reserveTokens: 40,000` against a **1M-token window** (your `glm-5.3-flash`), so auto-compact wouldn't fire until ~96% — you'd hit this wall long before that on every moderately-sized session.

I verified the fix path: re-running pi's own `prepareCompaction` on that session with a lower `keepRecentTokens` produces a valid compaction plan (18–29 messages cut at 2,000–4,000).
