## What it does

**The tool** (`ask_user`, a Gizmo custom tool wired into every session, like `run_script`):
- `{ question, options: [...] }` → multiple-choice; the tool appends a **"Write my own answer…"** sentinel to the options — picking it follows up with a free-text input request.
- `{ question }` alone → free-text input.
- The question renders **inline in the chat** — between the transcript and the composer — as an interactive card: "The agent is asking", the question, option buttons (or a text field), a countdown when the request has a timeout, and **Skip** (which returns "the user did not answer" to the agent so it can proceed or re-ask).
- Backed entirely by the existing extension-UI bridge (`ctx.ui.select`/`ctx.ui.input` → protocol → browser), so timeouts, abort signals (aborting the turn cancels the pending question), runtime eviction, and reconnect cleanup all come for free.

**Design choices worth knowing:**
- Select answers are still validated server-side against the offered options — that's why free text goes through the sentinel + input request rather than bypassing validation.
- Confirmations (`ctx.ui.confirm`) and editors stay modal dialogs; only `select`/`input` render in chat. Existing extension flows (e.g. Unity's compile confirmation) are untouched.
- `ask_user` is Gizmo-provided rather than a Pi extension for now — it's a UI capability of the shell, like the bridge itself. If you later want it available in plain `pi` TUI too, the same tool ports to a Pi extension (`registerTool` + `ctx.ui.select`) — that's the ask-user backend the bridge plan already anticipates.
