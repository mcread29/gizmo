## assistant

I’d add them through a **small adapter registry**, rather than treating either upstream repository directly as a Gizmo registry. Neither repository follows Gizmo’s `gizmo.registry.json` extension layout.

## Recommended structure

Create one registry repository, for example `gizmo-skill-registry`:

```text
gizmo.registry.json
extensions/
  pstack/
    index.ts
    pi-extension.ts
    package.json
    skills/
      ...
  matt-pocock-skills/
    index.ts
    pi-extension.ts
    package.json
    skills/
      ...
upstream-lock.json
scripts/
  update-upstreams.ts
```

Each adapter would be a no-op Pi extension with a package manifest exposing its skills:

```json
{
  "name": "gizmo-pstack",
  "private": true,
  "pi": {
    "skills": ["./skills"]
  }
}
```

```ts
// pi-extension.ts
import type { ExtensionAPI } from '@earendil-works/pi-coding-agent';

export const gizmoExtension = {
  id: 'pstack',
  name: 'pstack'
};

export default function pstack(_pi: ExtensionAPI) {}
```

Pi discovers nested `SKILL.md` files recursively, so both upstream layouts can remain intact beneath `skills/`.

## Vendor snapshots, don’t clone during installation

I recommend committing reviewed snapshots into the adapter registry and recording their exact commits:

```json
{
  "pstack": {
    "repository": "https://github.com/cursor/plugins",
    "path": "pstack/skills",
    "commit": "<sha>"
  },
  "matt-pocock-skills": {
    "repository": "https://github.com/mattpocock/skills",
    "path": "skills",
    "commit": "<sha>"
  }
}
```

An update script or scheduled GitHub Action should:

1. Fetch the pinned upstream commit.
2. Copy only the skill trees.
3. Preserve supporting files referenced by each `SKILL.md`.
4. Validate frontmatter and duplicate names.
5. Report shell scripts or harness-specific assumptions.
6. Open a reviewable update PR.

This is safer and more reproducible than downloading mutable upstream content during Gizmo’s registry build.

## Important compatibility caveats

### pstack

A substantial portion is Cursor-specific:

- Cursor model names and routing
- Cursor subagent types
- `/loop`, `/add-plugin`, built-in planning, and Cursor rules
- References to `cursor-team-kit`
- Graphite, PR automation, and bundled shell scripts

I would initially publish a **curated compatible subset**, not every pstack skill. General engineering principles, TypeScript guidance, TDD, writing, architecture, and review skills are better candidates than its orchestration modes.

### Matt Pocock’s skills

These are more portable, but some still assume:

- Claude/Codex invocation semantics
- GitHub or Linear integrations
- Bash-generated workflows
- Subagent behavior not identical to Pi
- Setup that writes project configuration

Again, expose individual skills so users can enable only what they want. Avoid enabling the whole collection automatically.

## Registry catalog

The registry should expose two independently installable entries:

```json
{
  "extensionsDir": "extensions",
  "extensions": [
    {
      "id": "pstack",
      "name": "pstack Skills",
      "description": "A reviewed, Pi-compatible subset of pstack."
    },
    {
      "id": "matt-pocock-skills",
      "name": "Matt Pocock Skills",
      "description": "Reviewed engineering and productivity skills."
    }
  ]
}
```

My preferred approach is therefore:

- **One adapter registry**
- **Two independently installable skill packages**
- **Pinned, vendored upstream snapshots**
- **Individual skills disabled by default**
- **Compatibility audit and selective inclusion**, especially for pstack
- **Automated update PRs rather than automatic mutable downloads**
