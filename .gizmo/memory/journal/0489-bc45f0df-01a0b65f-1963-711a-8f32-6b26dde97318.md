## 1. The 3 Primitives

| Need | Primitive | When to use |
|---|---|---|
| **One of a defined set** | **Choice** | Picks one option; distribution compares competing options. Use for routing, classifying into mutually-exclusive buckets. |
| **Degree along a described dimension** | **Score** | Probability-weighted position on ordered levels. Use for graded ranking, composite scoring. Levels must describe concrete situations and stand alone. Use comparable per-item Scores to rank. |
| **Whether a condition holds** | **Noul** | Probability of yes; **no separate confidence**. Use one per label when several may apply (multi-label). A Noul ~0.5 = yes/no equally likely, NOT medium intensity. |

Key distinction: Choice = exactly-one-wins. Noul = each condition independent yes/no. Score = how-much along an ordered scale.

## 2. State vs Instructions vs Criteria

* **State:** All relevant context the judgment needs — source text, identities, relationships, policies, current facts. Prefer named JSON fields when multi-part. Reference nested with backticked paths e.g. ``ticket.messages[0].text``. Strings OK for simple; objects/arrays when definitions/contrasts/exclusions/examples help.
* **Instructions:** The judgment itself — what to decide. Must contain complete meaning (question IDs are for code only, not sent to model). One narrow, coherent judgment per question. Split independently useful dimensions without destroying the relationship. Bounded action selection / contextual interpretation is valid.
* **Criteria:** Defines possible answers — options (Choice), levels (Score), yes-condition (Noul). Score levels must be concrete situations. Always include a no-match outcome when nothing may fit; use separate presence judgment when independently useful. For selection: model can't choose an omitted value — check candidate coverage.

> Code owns workflow; Jev supplies programmable common sense. Keep rules/calculations/lookups/execution in code.

## 3. Compose-and-Verify Rules

* **Parallel:** Ask independent questions over same state together — they run in parallel, can't see each other. Include useful speculative questions; state each speculative premise explicitly; code consumes applicable answers.
* **Sequential only when:** earlier answer needed to fetch evidence, construct new state, or determine next options.
* **Cost:** Extra questions cost tokens — measure budget/cost/latency.
* **Confidence handling:** Choice/Score confidence = distribution concentration, NOT workflow correctness or permission to act. Low confidence on harmless preference ≠ invalid. Several acceptable alternatives spreading probability is normal. Ignore uncertainty on unused branches.
* **Thresholds:** Evaluate on user's data + consequences. Weighted scores = compensating preferences; "any serious violation" needs separate conditions. Changing weight/display filter needn't rerun inference if evidence + meaning unchanged.
* **Validation:** Typed output guarantees interface, not truth. Test representative cases + app behavior. On failure inspect: exact state, questions, candidates, answers, composition, outcome. Separate: missing evidence vs model error vs code error vs service failure. Cookbook thresholds are examples, not universal rules. Credentials server-side.

## 4. Proposed Jev Questions — Developer Transcript Evaluation

Assumed state shape: `{ transcript.text, transcript.messages[], repo.context?, task.prompt? }`

**Q1 — Prompting specificity**
* Primitive: `Score`
* Instructions: `Judge how specific and actionable the developer's requests/prompts are in {transcript.text}. Consider goal, constraints, acceptance criteria, examples.`
* Criteria/levels: `L1-vague ("do stuff"/"fix it") / L2-partial-goal (goal but no constraints) / L3-specific (goal+constraints, no acceptance) / L4-fully-specified (goal+constraints+acceptance/examples)`
* State fields: `transcript.text`, `transcript.messages[].text+role`

**Q2 — Context completeness**
* Primitive: `Score`
* Instructions: `Judge whether the developer supplied sufficient context (files, errors, logs, repro steps, linked state) for the task in {transcript.text} to proceed without guessing.`
* Criteria/levels: `L1-missing (critical context absent) / L2-fragmentary (some files/errors, key gaps) / L3-adequate (enough to act, minor gaps) / L4-complete (files+errors+repro+constraints)`
* State fields: `transcript.text`, `task.prompt`, `repo.context`

**Q3 — Model-choice appropriateness**
* Primitive: `Choice`
* Instructions: `Given the task complexity and prompts in {transcript.text} with stated model in {transcript.model}, which model tier was appropriate?`
* Options: `under-powered (needed stronger reasoning) / appropriate / over-powered (simple task, cheaper model would do) / cannot-tell`
* State fields: `transcript.text`, `transcript.model`, `task.prompt`

**Q4 — Skill usage gap present**
* Primitive: `Noul`
* Instructions: `Does {transcript.text} show work where an available skill/procedure should have been invoked but was not (e.g. manual work a skill automates, violated best-practice the skill covers)?`
* Criteria: `yes = concrete missed-skill opportunity identifiable from transcript`
* State fields: `transcript.text`, `repo.available_skills[]`

**Q5 — Which skill gap (speculative, parallel with Q4)**
* Primitive: `Choice`
* Instructions: `Assuming a skill gap exists in {transcript.text}, which category best fits? If no gap, choose no-gap.`
* Options: `prompting/test-discipline / context-retrieval / code-edit-workflow / verification-lint-typecheck / no-gap`
* State fields: `transcript.text`, `repo.available_skills[]`

**Q6 — Followed verification discipline**
* Primitive: `Noul`
* Instructions: `Did the developer run checks (tests, lint, typecheck, build) or verify outcomes before declaring done in {transcript.text}?`
* Criteria: `yes = explicit verification step or output cited`
* State fields: `transcript.text`, `transcript.messages[].text`

**Q7 — Prompt iteration quality**
* Primitive: `Score`
* Instructions: `Judge how well the developer refined prompts based on prior outputs/failures in {transcript.text} (added evidence, narrowed scope, corrected assumptions vs repeated same vague prompt).`
* Criteria/levels: `L1-no-iteration (repeats/stuck) / L2-weak (minor rephrase) / L3-deliberate (adds evidence/narrows) / L4-exemplary (diagnoses failure, restructures)`
* State fields: `transcript.text`, `transcript.messages[].text+role`
