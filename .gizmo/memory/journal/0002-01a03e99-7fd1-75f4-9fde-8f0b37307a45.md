## assistant

The main change is to stop constructing a curated “Gizmo-flavored Pi” runtime in Pi Web mode and let Pi’s `DefaultResourceLoader` perform its normal discovery.

## Required changes

### 1. Separate Gizmo storage from Pi’s agent directory

Currently `~/.gizmo` is used for several unrelated things:

- Gizmo sessions
- copied Pi authentication/models/settings
- resources loaded into Pi

For “default Pi,” keep Gizmo’s sessions in `~/.gizmo`, but point Pi runtime/resource discovery directly at:

```text
~/.pi/agent
```

That removes the awkward auth-copy/re-import behavior and lets Pi use its real settings directly.

### 2. Use default resource discovery in Pi Web mode

The normal Gizmo path currently creates `DefaultResourceLoader` with:

```ts
noExtensions: true
noSkills: true
noPromptTemplates: true
noContextFiles: true
```

and manually supplies a curated set.

For Pi Web mode, instantiate the loader without those restrictions. That restores Pi discovery for:

- Global extensions: `~/.pi/agent/extensions`
- Project extensions: `.pi/extensions`
- Global skills: `~/.pi/agent/skills`, `~/.agents/skills`
- Project skills: `.pi/skills`, `.agents/skills`
- Prompt templates
- `AGENTS.md` context files
- packages configured in Pi’s `settings.json`
- extra extension/skill paths configured in Pi settings
- custom providers and models registered by extensions

The custom Gizmo/Unity system-prompt override should remain disabled.

### 3. Restore all default Pi tools

Pi Web should enable the normal built-ins rather than the current curated list:

```ts
read
bash
edit
write
grep
find
ls
```

On Windows, Pi may expose `powershell` according to its normal runtime behavior.

Gizmo extension tools can then be added alongside those defaults rather than replacing them.

### 4. Keep Gizmo extensions separate from Pi extensions

There are two extension systems:

- **Gizmo extensions**: Git, Unity, Svelte, activity, skill authoring
- **Pi extensions**: files/packages loaded by `DefaultResourceLoader`

Both can coexist:

- Keep Gizmo extensions loaded so the existing web UI and Git functionality work.
- Let Pi load its own extensions into `AgentSession`.
- Do not let Gizmo’s active workspace profile replace Pi’s system prompt in Pi Web mode.

### 5. Add project-trust handling

Pi only loads project-local executable extensions after the project is trusted. Gizmo needs a web-facing implementation for Pi’s trust prompt or a clearly configured default policy.

This is important because extensions execute arbitrary code with the user’s permissions. Silently trusting every workspace would be unsafe.

### 6. Bridge extension UI behavior

Most Pi extensions should work immediately if they only provide:

- tools
- lifecycle hooks
- prompt/context modifications
- providers
- skills/templates
- commands

TUI-specific extension features cannot render directly in Gizmo:

- `ctx.ui.custom()`
- custom TUI components
- custom tool renderers
- widgets, headers, footers, and terminal editor replacements

Those need either:

1. graceful no-op behavior in web mode, or
2. a protocol bridge to equivalent Gizmo dialogs, notifications, status items, and custom web contributions.

Basic `select`, `confirm`, `input`, and notifications are the most useful first bridge.

### 7. Add runtime reload support

Gizmo’s resource reload currently focuses on its own resource catalogue. “Default Pi” reload should call Pi’s session reload lifecycle so it reloads:

- extensions
- skills
- prompts
- context files
- packages
- provider registrations

This should ideally be exposed as one **Reload Pi runtime** action.

## Recommended implementation shape

Use two explicit session configurations:

```ts
createGizmoSession(...)
createDefaultPiSession(...)
```

Both should return the same Gizmo adapter that supplies model selection, compaction, commit-message generation, etc. Only their resource/tool configuration should differ.

That avoids the earlier bug where Pi Web returned early and accidentally omitted model-selection support.

## Expected limitations initially

With the backend changes alone, most non-TUI Pi extensions and all standard skills should work. Extensions whose value is primarily custom terminal UI will load, but their visual features will need dedicated web support.

This is a moderate backend refactor, not a new frontend. The existing full Gizmo UI should remain intact.
