Yes. The inspector ownership path is gone, but several legacy extension-boundary leaks remain:

1. **`activeDomains` / `domainId` terminology**
   - These are enabled extension IDs, not domains.
   - Rename toward `enabledExtensionIds`; retain protocol migration compatibility.

2. **Single global project service/status**
   - `hasProjectStatus`, `store.projectStatus`, `openProject()`, and `CompositeProjectService.#first()` still model one effective project-service owner.
   - Status/open operations should be scoped and keyed by extension.

3. **Unity settings in core**
   - `compilePlayModePolicy` remains in app settings and `WorkspaceLayout`.
   - It belongs in extension-owned persisted settings.

4. **Extension-specific core CSS**
   - Core CSS still knows IDs such as `unity`, `git`, and `activity`, plus Unity diagnostic selectors.
   - Extension bundles should own those styles; core should provide only generic panel primitives.

5. **Unity-shaped generic APIs**
   - `UnityStatus`, `UnityOpenProjectResult`, Unity-specific parsers, and some client errors remain in core.
   - These should become generic project/workspace contracts, with Unity types confined to the Unity extension.

6. **Minor stale coupling**
   - `GitCapability` still says “No Unity project is selected.”
   - The retained `showUnityInspector` references are intentional migration-only compatibility.

So: no extension owns the inspector anymore, but project services, settings, styling, and protocol naming still need another structural pass.
