## assistant

Journals are Gizmo's own long-term memory — your transcript history, written to disk as the conversation scrolls out of the model's live context. This is a feature you built in this repo, not a Claude Code thing.

## What they are

`.gizmo/memory/journal/` in each project:
- `0001-<sessionId>.md` … `0448-…` — **segments**. A chunk of conversation (user turns, assistant text, reasoning summaries, tool calls + results) rendered as markdown with YAML frontmatter.
- `index.jsonl` — one line per segment: id, session, first/last entry id, timestamp, message count, bytes, trigger.

You have 448 segments here. The sample I read (`0448`) is the tail of the TypeSafe-skill session from last night.

The design intent is stated in `apps/agent-server/src/memory/journal-store.ts:47` — the journal is **the authoritative half of memory**. Append-only, never rewritten, and no model is ever called to write it. A derived "knowledge layer" can be thrown away and rebuilt from these files.

## How they get written

`apps/agent-server/src/pi-extensions/memory-journal.ts` hooks four Pi lifecycle events, all best-effort and wrapped in a `guard` that swallows errors so journaling can never kill a session:

| Trigger | Fires on | Why |
|---|---|---|
| `compaction` | `session_compact` | The primary boundary. Records up to `firstKeptEntryId` exactly, so the segment ends where rebuilt context resumes — no duplicates. |
| `branch` | `session_before_tree` | Last chance before tree navigation makes the abandoned branch unreachable. |
| `threshold` | `turn_end` | Only if the un-journaled tail exceeds ~96 KB (`journal-recorder.ts:38`). Bounds what a crash can lose. |
| `session-end` | `session_shutdown` | Clean exit. |

`JournalRecorder` (`journal-recorder.ts`) owns the *policy*, `JournalStore` owns the *writing*. It tracks `resumeAfter` — the last entry id already journaled — so each append picks up exactly where the previous one stopped. Segment file is written first, then the index line, so a crash leaves an orphan file rather than a dangling index entry.

## How they get read

Two tools registered for the agent (`journal-tools.ts`):
- `journal_search` — lexical, no index; greps every segment body, returns ranked excerpts with ±3 lines of context, capped at 12 hits / 12 KB so results fit in context.
- `journal_read` — pulls one full segment by the id a search hit named (e.g. `"0042"`), capped at 48 KB.

There's a nice detail at `memory-journal.ts:44`: Gizmo replaces Pi's default system prompt wholesale when a workspace supplies one, which drops Pi's tool list — so the extension appends a one-line `journalAvailabilityLine` telling the model these tools exist, guarded against double-naming.

## Practical notes

- `GIZMO_MEMORY_JOURNAL=0` disables it entirely.
- `backfill.ts` / `backfill-cli.ts` import history from outside a live session; `claude-session-adapter.ts` reads Claude Code transcripts. That's what the `source: 'pi-archive' | 'claude-code'` field on a segment distinguishes.
- Your git status shows `index.jsonl` modified and two new `.md` files — that's just last night's session journaling itself. They're tracked in git, so they'll grow the repo over time; worth deciding deliberately whether you want that.

## assistant

Short answer: keep the raw transcript. It's the right *substrate* — the problem is that it's the only layer. The comments in `journal-store.ts:50` promise a "derived knowledge layer" that can be thrown away and rebuilt; that layer was never built, so `journal_search` is doing grep over 13 MB of markdown and the model has to reconstruct meaning from excerpts every single time.

## What the data says

- 449 segments, 13 MB, avg 27 KB each — **392 of them are `backfill`** (imported history), only 56 from live sessions.
- Only **1** `compaction` trigger ever fired, vs 45 `threshold`. Your "primary boundary" is essentially dead; segments are actually cut at an arbitrary 96 KB byte limit, which means they split mid-task.
- Search reads every segment body on every call (`journal-search.ts:43` is explicit that this is intentional). Fine now, quadratically annoying later.

So the failure mode isn't "transcripts are the wrong format." It's: retrieval is lexical-only, segment boundaries are arbitrary, and nothing is ever distilled.

## What I'd actually do

**Tier 1 — distill each segment at append time (biggest win by far).**

When a segment is written, kick off an async, best-effort digest with a cheap model (Haiku) and write it as a sidecar — `0448.digest.json` or extra frontmatter:

```
what happened · decisions made · files touched · errors hit · outcome (shipped/abandoned/blocked)
```

~300 tokens per segment. Your entire project history becomes ~150K tokens of *meaning* instead of 13 MB of raw turns. This preserves your core invariant: digests are derived, deletable, rebuildable from the segments, and a digest failure never blocks the session (same `guard` pattern you already have).

**Tier 2 — two-stage retrieval.**

`journal_search` searches digests first (small, dense, high signal-to-noise), returns segment ids ranked, and the model drills into raw segments with `journal_read` only when it needs the detail. That's the same shape as your current tools, just with the haystack 100× smaller. Lexical search over digests is genuinely good, because digests are prose about decisions, not JSON tool arguments.

**Tier 3 — a durable facts file with supersession.**

The thing digests still can't do: "we decided to use X, then three weeks later switched to Y." A small append-only `facts.jsonl` with `{claim, segment, at, supersedes}` gives you current-state memory rather than history. This is what actually stops re-litigating old decisions.

## Alternatives I'd skip or defer

- **Embeddings / vector store.** Defer. It adds derived state with an embedding-model dependency at write time, and at 13 MB your own comment is right that linear scan is fine. Revisit past ~100 MB, and even then digests-first gets you most of the win for a fraction of the complexity.
- **SQLite + FTS5.** Worth it eventually, but purely as an index — cheap, no model, rebuildable from the segments. Do it *after* digests; indexing raw transcripts faster doesn't fix that they're low-signal.
- **Full graph/entity memory.** Over-engineered for a single-developer project. Skip.

## Two things worth deciding regardless

1. **Segment boundaries.** Cut at semantic boundaries (turn-end after a task completes) rather than 96 KB. A digest of a coherent task is far more useful than a digest of "the middle of a task." Cheap fix: raise the threshold and make `turn_end` prefer a cut when the last turn ended without pending tool calls.
2. **Git.** 13 MB of transcripts are tracked and growing. I'd gitignore the journal and keep it machine-local — it's a cache of your history, not source. If you want it portable, sync it separately.

Want me to build Tier 1 + 2? It's additive — no changes to `JournalStore`'s append path, just a digest sidecar and a rewritten `journal-search` front end.

## The real multi-machine bugs

**1. `index.jsonl` conflicts on every concurrent session.** Both machines append lines to the same file at the same tail. Git sees a textual conflict every time. Fix is one line in `.gitattributes`:

```
.gizmo/memory/journal/index.jsonl merge=union
```

Union merge keeps both sides' lines. For an append-only log where line order doesn't matter (you sort by id anyway), that's exactly right — and it turns your worst merge case into a no-op.

**2. The `0449` id is a collision hazard.** Monotonic integers allocated from a local directory scan mean two machines both mint `0449-…md` for different content. Union merge won't save you — you get two different segments claiming the same id, and `journal_read("0449")` becomes ambiguous. The filename already carries a session UUID; the integer prefix is doing ordering work that the `at` timestamp could do instead. Either derive the id from session+sequence, or keep the integer purely as a display ordinal computed at read time from the index.

That second one is a live bug today, not a hypothetical — it just hasn't bitten because you've only been journaling from one box.

## What this means for the digest plan

It survives intact, and the multi-machine constraint actually makes the design *cleaner*:

- A segment is authored on exactly one machine, so its digest is generated on that same machine. Digest sidecars are per-segment files → same disjoint-write profile as segments → **zero merge conflicts**, no merge driver needed.
- Non-determinism stops mattering. Nobody ever re-digests someone else's segment, so two machines never disagree about the same digest.
- Commit the digests. They're small (~300 tokens each), they're the part the agent actually reads, and rebuilding them on a fresh clone would mean 449 model calls. That's precisely the "don't rebuild every time" cost you're trying to avoid — so the derived layer should be committed even though it's derivable.

The one thing worth keeping out of git is any *index* you build later (SQLite/FTS): binary, non-mergeable, and genuinely cheap to rebuild locally from committed segments and digests. That's the correct place to draw the line I drew in the wrong spot.

## What changed

**1. `.gitattributes` (new)**
```
.gizmo/memory/journal/index.jsonl merge=union
```
Verified with `git check-attr`. Parallel sessions on two machines now merge their index appends instead of conflicting.

**2. Collision-safe segment ids** — `journal-store.ts:192`

New `segmentId(number, firstEntryId)` produces `0449-9f293bd7`: the padded ordinal for ordering, plus the first entry's id for uniqueness. Entry ids are already unique per span, so two machines can't mint the same segment id even when they both allocate ordinal `0449`. Ordinals may still repeat across machines — only display ordering suffers, and `at` breaks the tie.

Your 449 existing segments keep their bare ordinals and still resolve, since `read()` matches the id recorded in the index and old ids remain unique among themselves. No migration.

**3. `journal_read` schema** — the id `maxLength` was 16, which the new format would have been close to crowding; raised to 64, and the description's example now shows the suffixed form so the model copies ids verbatim rather than truncating to four digits.
