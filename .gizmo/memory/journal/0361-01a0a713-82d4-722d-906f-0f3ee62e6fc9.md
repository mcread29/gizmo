## assistant

Good news: this machine is already on a tailnet as `genge.angler-musical.ts.net`, so most of this is within reach. But `https://gizmo.genge` exactly as you wrote it won't work — here's the shape of what's actually possible:

## Why not `gizmo.genge`

Tailscale's MagicDNS resolves the machine name itself — `genge`, and the full `genge.angler-musical.ts.net` — from every device on the tailnet. It does **not** resolve arbitrary subdomains of a machine name, so `gizmo.genge` would never resolve. There's no wildcard/subdomain support to exploit, in portless or otherwise.

## What portless `--tailscale` actually gives you

From the commands doc, `portless gizmo --tailscale …` (or `PORTLESS_TAILSCALE=1`) registers a **`tailscale serve --https=…` entry** on the machine's MagicDNS name. So you'd get:

- `https://genge.angler-musical.ts.net` (short `https://genge` works too from tailnet devices)
- …not `gizmo.<anything>` — the URL is **machine-scoped**, and additional apps get differentiated by **port** (`:8443`, `:8444`, …), not by name
- TLS is terminated by Tailscale itself with a publicly-trusted cert for your MagicDNS name — so **no CA install needed on any tailnet device**, unlike portless's own HTTPS mode

One caveat worth knowing: there's a [known bug (#280)](https://github.com/vercel-labs/portless/issues/280) where crashed sessions leak stale `tailscale serve` registrations, and each new run then climbs to the next port (`:8443`, `:8444`…). There's a [fix PR (#400)](https://github.com/vercel-labs/portless/pull/400), but check the portless version you install.

## You may not need portless at all

Since `tailscale serve` is doing the real work here, and your prod server is already a managed daemon on port 4173, the simplest version is one command against the already-running server:

```
tailscale serve --https=443 http://127.0.0.1:4173
```

That exposes the built app at `https://genge.angler-musical.ts.net` to the whole tailnet, with zero changes to how the server runs. (Portless's `--tailscale` would just be a wrapper around the same thing, plus its own proxy layer you don't need here.)

## The one Gizmo-side change, either way

Tailscale terminates TLS and forwards plain HTTP to `vite preview`, so the browser's origin becomes `https://genge.angler-musical.ts.net` — and today the server only allowlists `http://<host>:<port>` origins built from `GIZMO_WEB_HOSTS`. Two spots need that HTTPS tailnet origin:

1. **Vite preview `allowedHosts`** (else every request 403s on Host check)
2. **Agent-server WS `verifyClient`** (else the socket upgrade is rejected and the app loads with no backend)

That's the same small scheme-aware-host change from my last message, just with the tailnet hostname instead of `gizmo.localhost`. One subtlety: the `Origin` header matches exactly what you type in the address bar, so `https://genge` and `https://genge.angler-musical.ts.net` are *different* origins — allowlist both, or pick one canonical URL and stick to it.

Want me to make that allowlist change and try `tailscale serve --https=443` against the running prod server? If it works you'd have the tailnet URL live in a few minutes, and we can decide separately whether portless adds anything on top (for this use case, I suspect it doesn't).

## assistant

Yes — but the custom domain part lives outside Tailscale. Tailscale itself can't do it: MagicDNS only answers machine names (`genge`, `genge.angler-musical.ts.net`), there are no custom DNS records in MagicDNS, and `tailscale cert` only issues for the machine's own name. What Tailscale *does* give you is private transport: `100.105.88.93` is only routable from inside your tailnet, so any DNS name you point at it is effectively a private, tailnet-only hostname.

The recipe for `https://gizmo.<your-domain>`:

1. **DNS** — an A record like `gizmo.example.com → 100.105.88.93` (or a CNAME to `genge.angler-musical.ts.net`). Since `100.x` is unroutable on the public internet, this name resolves for everyone but only *works* for tailnet members. That's the property you want.
2. **TLS cert** — must be a publicly-trusted cert for your domain, which means a **DNS-01 challenge** (Let's Encrypt can't reach the tailnet IP for HTTP-01). This is the one fiddly bit, and it's why the standard tool here is **Caddy**: with a DNS-plugin build it issues and renews the cert automatically. Point it at the preview server:
   ```
   gizmo.example.com {
       bind 100.105.88.93      # tailnet interface only, not your LAN
       reverse_proxy 127.0.0.1:4173
   }
   ```
   (`/agent` websocket upgrades pass straight through to the preview server's own proxy, so nothing special needed there.)
3. **Gizmo-side** — the same allowlist change as before: `https://gizmo.example.com` in Vite preview `allowedHosts` + the agent-server WS origin list.

Why Caddy rather than portless for this: portless supports custom certs (`--cert/--key`) and multi-segment TLDs, but its proxy only listens on non-loopback in LAN mode, which [isn't supported on Windows](https://portless.sh/commands) — and genge is Windows. Caddy binds the tailnet IP directly with no such limitation, and handles cert renewal, which portless won't do for you.

One thing this doesn't solve: a custom domain that *only* resolves on one machine (via hosts file / `portless hosts sync`) is possible but it's per-device toil — the DNS-record version above works from every tailnet device including your phone, with zero per-device setup.

Do you own a domain you'd want to put this on? If so I can set up the Caddy config plus the Gizmo allowlist change; if not, the `tailscale serve` option from my last message gets you HTTPS on the tailnet today with no domain required.
