Yes — it makes sense, and it's actually the direction `docs/pi-extension-ui-bridge-plan.md` already points at, just taken to its logical endpoint. Here's the honest assessment.

## Why it makes sense

Right now Gizmo runs a **parallel, weaker copy of Pi's extension system**: `createTools`, `systemPrompt` fragments, `profile()`, `list`/`invoke` RPC, `createProjectService` — all duplicating things Pi extensions already do (`registerTool`, `promptGuidelines`, hooks, in-process state). Your own global extensions prove the point: `ask-user`, `subagents`, `workflows`, `search-and-scrape` already exist as Pi extensions with working tools. The Gizmo side would only ever be re-wrapping them.

Flipping the split gives you:

- **Pi extensions = capabilities.** Tools, commands, hooks, provider registration — portable across Pi's TUI, RPC, and SDK modes, maintained by Pi, loaded through the existing `additionalExtensionPaths` path.
- **Gizmo extensions = presentation.** A pure Svelte web bundle that pairs with a Pi extension id and renders richer UI than the generic bridge: a real subagents dashboard, a workflow run list, a nicer `ask_user`, Unity's inspector.

This also matches the bridge plan's core principle (line 23): *"A Pi extension should remain useful without a custom Gizmo frontend"* — UI is an optional enhancement layer, and a missing/broken UI bundle must never disable the backend.

## Would it work? Mostly yes, with three real problems to solve

**1. Data transport from Pi extension → Svelte UI.** This is the crux. Today `GizmoWebExtension.activate()` gets live ops via `GizmoServerExtension.list/invoke` over `ExtensionHostService` — if Gizmo extensions lose their server half, that pipe disappears. Three options, in increasing power:

- **Generic bridge, already works:** Pi extensions push state via `ctx.ui.setWidget/setStatus/notify`; a Gizmo UI extension intercepts and renders those requests natively instead of the generic renderer. Limited to what `ctx.ui` can express.
- **Declarative views over `pi.events`** — you've already prototyped this for the TUI (`pi-declarative-ui`, versioned views as widget lines, action routing). The same protocol works for web: Pi extension publishes view state, the paired Gizmo UI extension renders it as real Svelte; actions flow back browser → WS → `PiExtensionUiRuntime` → `pi.events.emit` into the runner. This is probably your sweet spot since `subagents`/`workflows` already speak it.
- **A true invoke RPC:** a generic `extension.invoke` message on the Gizmo WebSocket forwarded into the extension runner. This is what you'd need for anything interactive beyond view/action (e.g. Unity's command schemas). It replaces `list/invoke` with a Pi-side equivalent — small addition to `PiExtensionUiRuntime`, but it's new protocol, not existing plumbing.

**2. Extension attribution.** The bridge currently doesn't tell the web store *which* Pi extension emitted a UI request — `docs/pi-extension-ui-bridge-plan.md:13` lists "extension attribution in Pi" as a remaining phase. Pairing a UI bundle to a backend extension by id requires it. Until then, pairing can key on the `runtimeId`/source the requests do carry, or the declarative protocol can carry the extension id in its own envelope (your TUI version already does `extensionId`).

**3. What happens to the existing five Gizmo extensions.** The UI parts migrate cleanly (Svelte/Git/Activity panels, Unity console/inspector → Gizmo UI bundles). The backend parts become Pi extensions:
- Unity is the big one: `unity_*` tools → `pi.registerTool` over its existing RPC bridge; the project service (editor process watch, status) moves *inside* the Pi extension module — it's just TypeScript with full Node access, so nothing is lost. `confirm('stop_play_mode_for_compile')` becomes `ctx.ui.confirm` through the bridge, which already works generically.
- The `run_script` tool and the bounded tool policy (`pi-agent-service.ts:931`) dissolve — policy becomes Pi's `defaultTools` setting, which Pi Web mode already follows. Note this is a real trust-posture change: the "no shell by design" guarantee in `docs/extensions.md` goes away unless you keep a settings-level guard.
- `gizmo.extensions.json` stops listing capability packages and becomes a UI-bundle registry — or better, disappears: a Pi package could declare its frontend in its `pi` key (`{ "pi": { "extensions": [...], "ui": "./web" } }`), making backend + frontend one installable package. That's the endgame the bridge plan's Phase 8/9 describe.

## Verdict

The change is coherent, it deletes a lot of duplicated surface (`GizmoServerExtension` shrinks to ~`{id, name}`, the tool-policy derivation, `ExtensionHostService`), and every mechanism it needs either exists (bridge, `pi.events`, blob-bundle loading) or is already on the bridge plan's roadmap (attribution, custom frontend pairing). After your migration, every extension tool arrives via Pi's resource loader anyway, so the question is just: **who decides which *built-in* tools exist?** Two options:

**Option A — Pi's `defaultTools` setting.** Pi already has this (`docs/settings.md:221`): a `defaultTools` string[] in `settings.json`, with project-level override, controlling exactly the built-ins (`read`, `bash`, `powershell`, `edit`, `write`, `grep`, `find`, `ls`).
