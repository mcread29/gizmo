Keep `src/index.ts` as a compatibility barrel. Do not initially introduce subpath imports.

A file-only refactor does not require a protocol version bump; a shape change does.

### `apps/agent-server/src/sessions/pi-agent-service.ts`

This is the highest-risk server hotspot. It combines:

- Provider/auth management.
- Project/resource/tool-policy facades.
- Session creation, resume, deletion and naming.
- Active-session cache, LRU eviction and timers.
- Prompt, steering, attachment and compaction flows.
- Model and thinking-level selection.
- Event sequencing and transcript hydration.
- Confirmation and extension-UI lifecycle.
- Construction of the real Pi runtime.
- Resource discovery, trust resolution and model-runtime singleton management.

Extract leaves before splitting the service itself:

```text
apps/agent-server/src/sessions/
  pi-session-contract.ts
  pi-session-factory.ts
  pi-session-pool.ts
  pi-confirmation-broker.ts
  pi-agent-service.ts

apps/agent-server/src/providers/
  model-runtime.ts
  provider-service.ts
```

`pi-session-factory.ts` should receive explicit resource/model/extension dependencies rather than constructing `ResourceCatalogService` and reading global registries internally.

Migration risks:

- Extension UI is registered before session creation completes; an existing test depends on that ordering.
- Snapshot `lastEventId` and in-flight message splicing are race-sensitive.
- Streaming sessions must never be evicted.
- `modelRuntimePromise` must continue clearing rejected/auth-invalidated instances.
- Every service instance owns an interval and must be disposed.

## `packages/extensions`

Although small, the package mixes three unrelated concerns:

- Extension SDK contract: `src/extension.ts`
- Project runtime dispatch: `src/project-service.ts`
- Diff reversal utility: `src/patch.ts`

Recommended internal organization:

```text
packages/extensions/src/
  contracts/extension.ts
  project-service/project-service.ts
  project-service/composite-project-service.ts
  patch/revert-patch.ts
  index.ts
```

Keep current root exports during migration.

Additional concerns:

- `ProjectStatus` duplicates the protocol status shape even though the package already depends on `@gizmo/protocol`; these can drift.
- `GizmoServerExtension` mixes session tools/prompts, package resources, operation providers and project-service factories. Split into capability interfaces while retaining the existing aggregate interface.
- `CompositeProjectService` catches every error as “not handled.” A real runtime failure can therefore be hidden by a later provider. Introduce an explicit `ProjectNotHandledError` before changing dispatch behavior.
- `src/patch.ts` has no in-repository runtime consumers. Moving it to another package would be cleaner, but keeping the root re-export is safer for external extension authors.
- `ToolDefinition` directly couples the SDK to the exact Pi package API.

## Import and configuration implications

- `apps/agent-server/tsconfig.json` already includes both `src/**/*.ts` and `tests/**/*.ts`.
- Moving tests in `packages/protocol` and `packages/extensions` requires changing each `tsconfig.json` to include `tests/**/*.ts`.
- Relative test imports must change from `./module` to `../../src/...` as appropriate.
- Keep public integration tests importing `src/index.ts`; internal unit tests may import exact modules.
- Existing `vitest run` scripts discover both layouts without configuration. After migration, a package-level `vitest.config.ts` or explicit `tests/**/*.test.ts` include would enforce the convention.
- Keep package root exports stable:
  - `packages/protocol/package.json` exports `./src/index.ts`
  - `packages/extensions/package.json` exports `./src/index.ts`
- Avoid subpath imports until an `exports` map is deliberately added.
- Protocol has the largest blast radius: references appear in 52 app files and 23 agent-server files. Root-barrel compatibility is essential.
- `@gizmo/extensions` is referenced almost entirely by agent-server, but external dynamically loaded extensions may also compile against its API.

## Prioritized phases

1. **Baseline and test organization**
   - Fix portable path assertions/containment.
   - Move all tests under `tests/`.
   - Add registry-manager, composite-project-service and concurrency characterization tests.
   - Establish a fully green baseline.

2. **Low-risk shared primitives**
   - Expand `apps/agent-server/src/path-utils.ts`.
   - Add `config/data-paths.ts`, `io/atomic-file.ts`, and `concurrency/async-mutex.ts`.
   - Remove imports of data-path configuration from session repository code.

3. **Protocol decomposition**
   - Split schemas, requests, events and parsers.
   - Preserve `packages/protocol/src/index.ts` as the sole public barrel.
   - Run agent-server and app checks/tests after every domain extraction.

4. **Extension contracts and server catalogs**
   - Reorganize `packages/extensions`.
   - Unify project status types.
   - Split project catalog, resource discovery and registry management.
   - Add explicit unsupported-project semantics before changing composite routing.

5. **Transport decomposition**
   - Extract request routing, handlers, connection lifecycle and watch coordination.
   - Inject registry/bundle dependencies.
   - Preserve event ordering and shutdown behavior.

6. **Session runtime decomposition**
   - Extract factory/model runtime first.
   - Then confirmation/UI brokers and the active-session pool.
   - Leave `PiAgentService` as a thin session application facade.

7. **Compatibility cleanup**
   - Remove deprecated aliases only after all app and extension consumers migrate.
   - Consider subpath exports or a separate patch package only in a versioned API change.
