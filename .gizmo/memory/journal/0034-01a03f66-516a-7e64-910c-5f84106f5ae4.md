## Conclusion

Pi Web should remain an **in-process Pi SDK session behind `PiAgentService`**. Do not switch to `InteractiveMode` or `runRpcMode`; that would bypass Gizmo’s WebSocket protocol, session repository, attachments, project integrations, tool rendering, confirmations, model picker, and frontend shell.

The current uncommitted Pi Web branch is directionally correct—default `DefaultResourceLoader`, no explicit tool allowlist, and Gizmo tools remain additive—but it is not yet equivalent to normal Pi discovery or lifecycle behavior.

### Default discovery

With `cwd`, `agentDir: getAgentDir()`, and an uncustomized `DefaultResourceLoader`, Pi 0.84.2 discovers:

| Concern | Source |
|---|---|
| Extensions | `~/.pi/agent/extensions`, `.pi/extensions`, settings paths, packages |
| Skills | `~/.pi/agent/skills`, `~/.agents/skills`, `.pi/skills`, ancestor `.agents/skills`, packages |
| Prompts | `~/.pi/agent/prompts`, `.pi/prompts`, settings paths, packages |
| Context | global `AGENTS.md`, then ancestor/current `AGENTS.md`/`CLAUDE.md` |
| System prompt | global/project `SYSTEM.md`, `APPEND_SYSTEM.md` |
| Packages | `settings.json` `packages`, under agent/project `npm/` and `git/` |

| Models/auth | `models.json`, `auth.json`, environment, built-ins |
| Themes | global/project/package themes, although Gizmo Web cannot render Pi themes |

Pi 0.84.2 defines seven built-in tools:

- `read`
- `bash`
- `edit`
- `write`
- `grep`
- `find`
- `ls`

The default active set is `read`, `bash`, `edit`, `write`. `settings.defaultTools` can replace it. Unlike 0.84.3, this installed version has no `powershell` built-in.

## Required creation path

Use `createAgentSessionServices()` followed by `createAgentSessionFromServices()`, not the current manual loader plus `createAgentSession()`.

`createAgentSessionServices()` performs an important extra step:

1. Loads extensions.
2. Applies pending `pi.registerProvider()` registrations to `ModelRuntime`.
3. Refreshes local model composition.
4. Only then allows session/model selection.

With direct `createAgentSession()`, initial model selection happens before extension provider registrations are flushed. Therefore a provider supplied by a Pi extension may not:

- Be eligible as the initial/default model.
- Appear when Pi determines whether any model is available.
- Restore correctly from a saved session.

Recommended Pi Web shape:

```ts
const agentDir = getAgentDir();

const services = await createAgentSessionServices({
	cwd,
	agentDir,
	settingsManager,
	resourceLoaderReloadOptions: trustReloadOptions,
});

const { session, extensionsResult } =
	await createAgentSessionFromServices({
		services,
		sessionManager,
		customTools: gizmoTools,
		// Deliberately omit `tools`.
	});
```

Omitting `tools` is essential:

- Pi applies `settings.defaultTools` or its standard four defaults.
- All Pi-extension tools are activated.
- All Gizmo `customTools` remain additive.
- Dynamic extension tools are not blocked by a fixed allowlist.

The normal non-Pi-Web path should retain its current restricted allowlist.

## Problems in the current partial implementation

### 1. Hard-coded agent directory

`defaultPiAgentDir()` uses `homedir()/.pi/agent`. It does not respect:

- `PI_CODING_AGENT_DIR`
- Rebranded Pi configuration
- Pi’s own path normalization

Use exported `getAgentDir()` instead. This is the canonical API in:

- `.../dist/config.js`
- `.../dist/config.d.ts`

### 2. Project trust is currently bypassed

This is the most serious issue.

`SettingsManager.create()` defaults `projectTrusted` to `true`. Calling:

```ts
new DefaultResourceLoader(...);
await loader.reload();
```

without trust orchestration will load and execute project `.pi` resources immediately.

That includes:

- `.pi/settings.json`
- project extensions
- project packages and automatic package installation
- project `SYSTEM.md`
- `.agents/skills`

Normal Pi’s CLI performs a bootstrap load with project trust disabled, resolves trust, and then reloads. See `dist/main.js`, approximately the block using:

- `ProjectTrustStore`
- `hasTrustRequiringProjectResources`
- `resourceLoaderReloadOptions.resolveProjectTrust`

For headless Gizmo Web, the safe initial policy is:

1. No trust-requiring resources: trust.
2. Saved `trust.json` decision: use it.
3. No saved decision:
   - `defaultProjectTrust: "always"`: trust.
   - `"ask"` or `"never"`: do not trust.
4. Later add a Gizmo trust dialog if `"ask"` should be interactive.

Important limitation: Pi’s internal `resolveProjectTrusted()` and `emitProjectTrustEvent()` are not exported from the package root, even in 0.84.3. A host cannot reuse the complete CLI policy, including global extensions’ `project_trust` handlers, through a supported public import. Options are:

- Implement the safe non-interactive subset above.
- Add a small upstream export.
- Duplicate the CLI policy, accepting maintenance risk.

Do not import blocked internal package subpaths.

### 3. Extension startup is never bound

`createAgentSession()` constructs an `ExtensionRunner`, so tools and most hooks exist, but `session_start` and `resources_discover` are only emitted by:

```ts
await session.bindExtensions(...)
```

Current `PiAgentService` never calls it. Consequently:

- `session_start` initialization does not run.
- Extension-contributed resource paths from `resources_discover` are absent.
- Long-lived extension state may never initialize correctly.
- Extension errors are not routed into Gizmo.

At minimum:

```ts
await session.bindExtensions({
	mode: 'print',
	onError: reportExtensionError,
});
```

Providing `onError` also ensures `AgentSession.reload()` performs the post-reload `session_start` path. A proper remote UI adapter would use mode `"rpc"` plus a custom `ExtensionUIContext`.

### 4. Disposal skips `session_shutdown`

`AgentSession.dispose()` invalidates extensions but does not emit `session_shutdown`.

Current eviction and deletion paths call it directly in:

- `PiAgentService.#evict()`
- `PiAgentService.dispose()`
- `PiAgentService.deleteSession()`

Extensions that start subprocesses, watchers, sockets, or timers can leak them. `AgentSessionRuntime.dispose()` does emit `session_shutdown`, but the current service does not use that runtime abstraction.

Either:

- Store `AgentSessionRuntime` and call `await runtime.dispose()`, or
- Add an async host-owned shutdown wrapper that emits `session_shutdown`, then disposes.

This requires changing `PiSessionLike.dispose()` and eviction paths to be asynchronous or explicitly tracking pending shutdown promises.

### 5. Shared `ModelRuntime` leaks project extension providers

`gizmoModelRuntime()` is a process-wide singleton. That is reasonable for the current Gizmo-owned configuration, but unsafe with project-specific Pi extensions:

- One project may register or override a provider used by another session.
- A reload/unregister in one session can affect another.
- Project extension providers can remain after a different project loads.
- `listProviders()` does not load resource extensions, so it will omit extension-provided providers anyway.

For Pi Web, prefer cwd-bound `ModelRuntime` instances created by `createAgentSessionServices()`. Make provider listing resource/cwd-aware or derive the model catalog from the active session.

### 6. Gizmo’s resource UI becomes inaccurate

`ResourceCatalogService` explicitly disables Pi discovery and reports only Gizmo-owned folders:

- `apps/agent-server/src/resources/resource-catalog.ts`
- `apps/agent-server/src/resources/resource-paths.ts`

Meanwhile Pi Web sessions would load `~/.pi/agent` directly. Therefore Settings → Agent could say a skill is disabled while the session actually loads it, and its install/enable controls write `~/.gizmo/resources.json`, which Pi Web ignores.

For Pi Web:

- Build the displayed catalog from the same effective Pi `ResourceLoader`.
- Treat Pi settings/package filters as authoritative.
- Initially make the Pi catalog read-only if package/filter mutation is out of scope.
- Do not present Gizmo’s skill toggles as controlling Pi Web sessions.

### 7. `reimportPiAuth()` has misleading semantics

The partial change turns `providers.import-pi-auth` into “clear the runtime cache and list providers” in Pi Web mode. Since Pi Web already reads Pi auth directly, the operation should either:

- Be hidden/disabled in Pi Web, or
- Be renamed to refresh provider state.

It should not claim to import anything.

## System prompt composition

Suppressing `systemPromptOverride` in Pi Web is correct; otherwise Gizmo replaces Pi’s entire default prompt and loses Pi’s tool guidance and normal prompt structure.

If Gizmo integration guidance must remain, append it rather than replace Pi:

```ts
appendSystemPromptOverride: (base) => [
	...base,
	activeDomains.systemPrompt!,
]
```

Preferably split `activateExtensions()` so only integration-specific guidance is appended; its current `coreSystemPrompt` duplicates Pi’s base role instructions.

## UI limitations

Pi extensions assume one of four modes: `tui`, `rpc`, `json`, or `print`; there is no `web` mode.

Without a custom `ExtensionUIContext`:

- `ctx.hasUI` is false.
- Select/confirm/input return cancellation defaults.
- Notifications, widgets, status, title, and editor operations are no-ops.

Even with an RPC-style Gizmo adapter, these remain TUI-only or degraded:

- `ctx.ui.custom()`
- custom TUI components
- custom footers/headers/editors
- Pi themes
- keyboard shortcuts
- tool `renderCall`/`renderResult`
- message/entry renderers
- Markdown transformers

Additional current Gizmo gaps:

- Custom extension messages are ignored by `PiEventTranslator`.
- `entry_appended` is ignored.
- Pi command discovery is not exposed to the web client.
- Prompt templates and extension commands work if manually typed, but are absent from autocomplete.
- Built-in commands such as `/reload`, `/settings`, `/trust`, and `/model` do not execute through `session.prompt()`.

A later generic UI adapter can mirror Pi RPC’s protocol for:

- `select`
- `confirm`
- `input`
- `editor`
- `notify`
- `setStatus`
- string-array `setWidget`
- `setTitle`
- `setEditorText`

Gizmo should continue using its own web-extension renderers for tool presentation.

## Reload limitations

`AgentSession.reload()`:

- Reloads settings, packages, extensions, skills, prompts, themes, context, `SYSTEM.md`, and `APPEND_SYSTEM.md`.
- Emits `session_shutdown`.
- Invalidates the old extension context.
- Rebuilds tools and extensions.
- Emits `session_start`/`resources_discover` only if extension bindings exist.
- Applies only to that resident session.

It does not:

- Reload Gizmo extensions from `gizmo.extensions.json`; those are server-startup resources.
- Reevaluate project trust automatically.
- Expose a built-in `/reload` command through the SDK prompt path.
- Automatically reload every active/idle Gizmo session.
- Reliably make changed `models.json` a completed refresh barrier.
- Reapply a changed `settings.defaultTools` set; reload preserves the current active tool names.

Add an explicit `session.reload` Gizmo request that:

1. Rejects while streaming.
2. Re-resolves trust if requested.
3. Calls `session.reload()`.
4. Awaits `modelRuntime.refresh({ allowNetwork: false })` for local provider/model changes.
5. Emits updated tools/models/resource diagnostics.
6. Makes clear it reloads only the selected session.
