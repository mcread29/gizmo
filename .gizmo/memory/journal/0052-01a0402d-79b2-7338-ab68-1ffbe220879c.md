## Current implementation

### Workspace UI

- `apps/app/src/lib/features/workspace/WorkspaceScreen.svelte`
  - Exposes only **Overview** and **Configure** tabs.
  - Mounts `WorkspaceConfigurePanel` for all profile, extension, skill, and workspace settings.
  - This differs from `docs/workspace-profiles.md`, which describes separate Overview, Profile, and Settings tabs.

- `apps/app/src/lib/features/workspace/WorkspaceConfigurePanel.svelte`
  - Owns the entire editable draft locally: `setup`, `saved`, `editingId`, `saving`, and errors.
  - On workspace change it calls:
    1. `store.refreshResources(path)`
    2. `store.detectProject(path)`
  - Combines detected extension templates with `StoredProject.profiles`.
  - Treats profiles as editable only when `source` starts with `workspace`.
  - Built-in and extension profiles are locked and require **Duplicate to edit**.
  - Extension rows are sourced from `ProjectDomains.domains` and display “Detected in this workspace” or “Not detected”.
  - Enabling an extension uses its detected root or `"."`.
  - Although a non-root path is displayed, there is currently no control for editing that root.
  - Dirty tracking uses `JSON.stringify`, so ordering/default normalization is significant.
  - `base` inheritance is only interpreted in this component for difference markers and revert actions.

- `apps/app/src/lib/features/workspace/WorkspaceHome.svelte`
  - Reads `project.integrations`, i.e. the active profile’s extension list, for its extension summary.

- `apps/app/src/lib/features/settings/AgentSettings.svelte`
  - Manages global skills/resources only.
  - There is no global installed-Gizmo-extension catalog UI.

- `apps/app/src/lib/extensions/ExtensionSettings.svelte`
  - Renders extension-specific settings only for `activeDomains`.
  - It is not the extension-selection surface.

### Workspace creation

### Global extension loading

- `gizmo.extensions.json` is the actual global installation allowlist.
- `server.ts` loads it through `loadServerExtensions()` and `registerExtensions()`.
- `registry.detectExtensions()` exposes only extensions with detection hooks.
  - Git, Activity, and Skill Authoring therefore cannot appear in the workspace selector.
- The web registry in `registry.svelte.ts` always includes statically bundled Svelte, Git, and Activity, independently of what the server loaded.
- `App.svelte` calls `installWebExtensions(agentClient)` before `store.connect()`. With the real WebSocket client, `extensions.web` can therefore run before the socket is connected and degrade to a warning.

### Extension activation leaks

Workspace enablement is not consistently respected:

- `ExtensionDialogs.svelte` and `ExtensionSettings.svelte` filter by `activeDomains`.
- `WorkspaceInspector.svelte` renders static `inspectorTabs` from every web extension.
- `Titlebar.svelte` renders every extension’s `statusBar`.
- `CommandPalette.svelte` renders every extension’s static commands.
- Git contributes `defaultTools`, so `git_status` is available to every session regardless of workspace selection.
- `AgentStore.selectWorkspace()` refreshes Git and project status unconditionally.

### Profile/runtime gaps

Several current controls are not enforced by the backend:

- `WorkspaceProfile.tools.mode` is saved but extension tools are always added by `activateExtensions()`.
- `WorkspaceProfile.prompt.mode` is saved but extension prompt fragments are always composed in normal Gizmo mode.
- `base` is not resolved server-side.
- Canonical defaults are copied into the project, so unchanged workspaces cannot receive updated extension defaults.
- Session creation passes integrations rather than a profile ID/effective profile.
- `listSessions()` and `resumeSession()` replace session integrations with the workspace’s current active profile, so existing threads do not reliably retain the configuration they started with.

## Recommended model

I would interpret “enabled per project” as a workspace-level allowlist. Profiles may activate/configure only extensions enabled for that workspace.

Persist a versioned project configuration such as:

```ts
{
  version: 2,
  enabledExtensions: [{ id: 'svelte', root: 'apps/app' }],
  activeProfileId: 'default',
  profileOverrides: [
    // Patches for canonical defaults; omitted when empty
  ],
  profiles: [
    // Normal user-created profiles; always persisted
  ]
}
```

Key rules:

1. **Canonical profiles are not written to the workspace.**
   - Core contributes `default`.
   - Each globally installed extension may contribute a canonical default.
2. **Editing a canonical profile creates a temporary draft override.**
   - Save persists only its patch.
   - Reverting the final difference removes the override.
   - An unchanged profile therefore resolves directly from the current canonical definition.
3. **New profiles are normal project-owned records.**
   - They remain persisted even if their effective values happen to match a default.
   - They can be renamed, activated, duplicated, and deleted normally.
4. **Extension roots belong to workspace extension enablement**, not duplicated across every profile.
5. **Profiles reference enabled extension IDs**, and the server joins them to workspace roots when composing a session.
6. Disabling an extension should be blocked while a profile references it, with the dependent profile names shown. This avoids silently destroying profile configuration.

- Keep `ExtensionDescriptor` for live project-hosted extensions; do not overload it for Gizmo packages.

In `packages/extensions/src/extension.ts` and server registry:

- Remove `detect` and `detectRoots`.
- Rename/generalize `profile(root)` into a canonical default-profile contribution.
- Add a registry catalog that returns every loaded extension, including web-only extensions.
- Validate duplicate extension IDs and duplicate canonical profile IDs.
- Validate enabled extension IDs against `registeredExtensions()`, not filesystem detection.

In `ProjectCatalog`:

- Replace detection-based profile creation with a blank v2 configuration:
  - active canonical `default`
  - no enabled extensions
  - no overrides or custom profiles
- Resolve canonical + override + custom profiles server-side.
- Normalize empty canonical overrides out before writing.
- Migrate v1 files:
  - canonical `builtin:`/`extension:` entries become patches only when changed;
  - `workspace:` entries become custom profiles;
  - union existing integrations into `enabledExtensions`.
- Preserve idempotency when an already registered workspace is selected again.

## Likely tests

### Frontend

- `CommandPalette` adds a folder without calling detection.
- New workspace starts with Default and no enabled extensions.
- All globally installed extensions appear, including non-detectable/web-only ones.
- No “Detected”/“Not detected” copy remains.
- Root editing supports nested paths such as `apps/app`.
- Canonical profile fields are editable without duplication.
- First change creates “Customized”; resetting the final change removes it.
- Saving an unchanged canonical profile sends no override.
- Saving a changed canonical profile survives tab remount/reconnect.
- A new custom profile remains a normal profile even when equal to Default.
- Disabling a referenced extension is blocked accessibly.
- Disabled extension commands, tabs, status items, settings, and dialogs are absent.
- Update existing profile tests in `App.test.ts`; add focused panel tests rather than continuing to grow the full-app suite.

### Server/protocol

- Installed catalog returns every registered extension without filesystem inspection.
- `project.add` performs no detection and writes no canonical profile copies.
- Unknown extension IDs and roots outside the workspace are rejected.
- Canonical defaults update when unchanged.
- Overrides survive canonical updates and disappear when empty.
- v1 profile files migrate deterministically.
- Tool and prompt modes affect actual session composition.
- Existing sessions retain their original effective profile.
- Protocol parsing and WebSocket client request tests cover the new endpoints.

### Extension surfaces

- Git tools/status/commands are absent until Git is enabled.
- Activity inspector is absent until Activity is enabled.
- Runtime web bundles load only after connection.
- Built-in web definitions do not surface when their server extension is not installed.

The central architectural requirement is to stop treating detected effective profiles as persisted truth. Installed extensions, workspace enablement, canonical defaults, temporary overrides, and custom profiles need to become separate concepts.
