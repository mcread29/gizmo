**1. Project integrations — already there and toggleable.** `fake-client/fixtures.ts` seeds five (`unity`, `svelte`, `git`, `activity`, `skill-authoring`) and assigns three to ThirdPersonSandbox. The Configure tab's toggles work in fake mode: they write to `gizmoOverrides` and `syncIntegrations()` rebuilds `project.integrations`. Add more by appending to `fakeDomains` / `createFakeProjects()`.

**2. Extension operations — partly.** `FakeExtensionCapability.invoke` hand-implements `git status`, `git commit`, and a Unity console snapshot. Anything else throws `Unknown extension operation`.

**3. Inspector tabs (the "Ollama" tab in your screenshot) — not wired, but the hook exists.** Those tabs come only from runtime-loaded web extension *bundles*, and `main.ts` constructs `new FakeAgentClient()` with no options, so `listWebExtensionBundles` stays `undefined` and the registry is empty — hence "No inspector extensions enabled". `FakeAgentClientOptions.webExtensionBundles` already exists (a test passes `{ bundles: [], diagnostics: [] }`); it's just never populated for `?fake`.

So if what you want is to iterate on inspector/right-panel UI against fake data, that's a small change: seed `webExtensionBundles` in `main.ts`'s fake branch with a stub bundle contributing an inspector tab. Want me to wire that up?

One design call worth naming: they register straight into the web-extension registry rather than going through `listWebExtensionBundles` → blob-URL loader. The loader's job is safely evaluating untrusted *source strings*, and stubs would have to be hand-written as source to use it — which buys nothing for UI iteration and costs real Svelte components. Registration happens inside the existing dev-only `?fake` branch of `main.ts`, so none of it reaches a production bundle. If you'd rather exercise the bundle-loading path too, that's a separate and larger piece of work.
