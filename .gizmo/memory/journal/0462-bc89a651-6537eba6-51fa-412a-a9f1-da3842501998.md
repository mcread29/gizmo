**Root cause of the compaction error.** Pi's manual `compact()` stores its abort controller on the session, awaits the summary, then reads `this._compactionAbortController.signal` again. Its `finally` also clears that field. When two compactions overlap on one session, the second one's cleanup wipes the field out from under the first, which then crashes with "Cannot read properties of undefined (reading 'signal')". Gizmo had two callers that could overlap: the post-run overdue compaction in the runtime pool, and the manual compact request, which only checked for streaming, not for a compaction already in flight.

**Fixes made**

- `patches/@earendil-works__pi-coding-agent@0.84.4.patch` now also rewrites `compact()` to use a local controller, refuse a second call with "Compaction is already in progress", and only clear its own controller. Reapplied via pnpm, lockfile hash updated.
- `apps/agent-server/src/sessions/session-operations.ts` rejects a manual compact while Pi reports `isCompacting`.
- `apps/agent-server/src/sessions/compaction-fallback.ts` and the runtime pool skip the overdue compaction when one is already running, and the failure stack is now logged to server.log so the next occurrence is diagnosable.
- Per-thread compacting UI: the client now tracks `compactingSessions` by session id, derives the selected thread's flag on switch, and scopes the manual compact's flag reset to the thread that started it. The server also re-announces an in-flight compaction when a client attaches, so a reload mid-compaction shows the right state.
