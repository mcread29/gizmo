You’re right—it’s explicitly conditional:

```svelte
{#if store.usage}<UsageMeter usage={store.usage} />{/if}
```

`store.usage` is cleared when switching/resuming sessions and after compaction. It only returns after an assistant response emits a new `session.usage` event. So the context meter genuinely disappears during those gaps; it isn’t merely hidden by layout. This is a UI/state-handling bug or unfinished empty state.

Yes—that matches the code. The compact button is always rendered, but the meter only renders when `store.usage` exists.

## user

why does it sometimes not exist? why does it not know?

## assistant

Because the app currently **doesn’t calculate or restore usage itself**. It only learns context usage from a completed assistant response’s Pi usage metadata.

It deliberately clears that value:

- when creating or switching sessions;
- while resuming a session;
- after compaction, because the old measurement is no longer accurate.

A new `session.usage` event is emitted only when an assistant message completes **and includes valid usage data**. Until that happens—or if the provider omits usage metadata—`store.usage` remains `undefined`, so the meter isn’t rendered.

So Pi may have enough session data to estimate usage, but Gizmo currently doesn’t request/restore that estimate. It waits for the next provider-reported measurement.

## user

literally in the same thread it just disappeared randomly

## assistant

Within the same thread, the likely trigger is **automatic compaction**.

When Gizmo receives `session.compaction` with `active: false`, it explicitly does:

```ts
state.usage = undefined;
```

That immediately removes the meter. It stays absent until another assistant response reports fresh usage. Because compaction may happen automatically and quickly, it can look random—especially if you don’t notice the brief “Compacting context…” label.

So it’s deterministic, but the UI makes it look random by silently removing the meter instead of displaying “usage recalculating.”
