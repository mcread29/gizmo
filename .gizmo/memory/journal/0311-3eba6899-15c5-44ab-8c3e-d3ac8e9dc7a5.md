## Journal layer — `apps/agent-server/src/memory/`

**`journal-normalize.ts`** — span → markdown. User and assistant prose is never trimmed; reasoning, tool arguments, and successful tool results get head+tail truncation with a dropped-char count; **errors are kept whole**, since an error is short and is usually why a later decision was made. Tool results are titled by the call they answer, so a segment reads without cross-referencing ids.

**`journal-store.ts`** — append-only segments plus `index.jsonl`. Segment file is written tmp+rename *before* its index line, so a crash mid-append leaves an unreferenced segment rather than a dangling index entry — the recoverable direction. A torn final index line is skipped rather than throwing. `lastEntryIdFor(sessionId)` is the gap/overlap guarantee: callers slice the branch from just past it.

**`journal-recorder.ts`** — the triggering policy, separated so it's testable without a filesystem. `record(session, { trigger, until })` takes `until` for the compaction case — pass `firstKeptEntryId` and the segment ends exactly where live context resumes, so the kept messages aren't journaled twice. `recordIfLarge()` is the crash-insurance path at 96KB.

No model calls anywhere in this layer — journaling has to keep working when extraction is unavailable, which is the whole reason the two layers are separate.

## Where it lands right now

| What | Path | Scope |
|---|---|---|
| Archived transcripts | `~/.gizmo/sessions/archived/*.jsonl` | global |

## Is JSONL + raw markdown right?

Mostly yes, with one part I'd change.

**Markdown segments: keep.** Three reasons that actually hold:

1. The consumer is a language model. Markdown is what it reads best, with no parse or escape layer between storage and prompt. Storing raw `AgentMessage` JSON and re-rendering at read time buys nothing and costs a serialization round-trip on every retrieval.
2. It's greppable and human-inspectable. When a derived fact looks wrong, you `rg` the journal and read the actual conversation. That debugging loop is the main thing the journal exists for.
3. Append-only means the usual objection to files — update cost, rewrite races — never applies.

And there's a justification I couldn't have made before the archive change: **the journal is now allowed to be lossy.** The raw JSONL survives in `sessions/archived/`, so normalization dropping 90% of tool output isn't destroying the last copy. The journal is a derived, readable projection; the archive is the true raw. Before archiving, aggressive truncation would have been throwing away evidence.

**`index.jsonl`: this is the weak part, and you're right to poke at it.** It duplicates the frontmatter that's already in every segment file, so there are two sources of truth that can disagree — exactly the failure mode the design is supposed to avoid. I kept it because `lastEntryIdFor()` runs on every append and scanning N files to answer it is silly.

The fix is small: keep the file, but declare the frontmatter authoritative and the index a **rebuildable cache**, plus a `rebuildIndex()` that regenerates it by scanning segment frontmatter. Then a corrupt or deleted index is a non-event rather than data loss, and the "two sources of truth" objection goes away because one of them is disposable. That needs a frontmatter parser, which the store doesn't have yet — `renderSegment()` writes YAML by hand and nothing reads it back.

## Where SQLite actually earns its place

Not here. The journal's entire workload is *append* + *scan in order*, which files do perfectly and SQLite adds nothing to.

It earns its place at **layer 2**, which has a genuinely different shape. Facts need: filter by `status: current`, traverse `supersedes` chains, find every fact citing segment `0007`, resolve `[[wikilinks]]` — and `journal_search` needs ranked full-text over hundreds of segments, where grep gets both slow and bad at ranking. FTS5 is the right tool for that and shell-out grep is not.

So the principle I'd hold to as this grows:

> **Files are the source of truth. SQLite is a derived index you can delete.**

Segments and fact bodies stay as markdown on disk — git-diffable, hand-editable, and rebuildable. The database holds only what's reconstructible from them: the FTS table, the citation graph, the status filter. If it corrupts, `rm memory/index.db` and rebuild. That keeps the property that makes this architecture worth building — you can throw away everything derived and regenerate it from the journal — while getting real queries where you need them.

Concretely: don't add SQLite now. Add `rebuildIndex()` to the journal, and introduce the database when you build the facts layer, as a pure cache alongside `facts/*.md`.
