## assistant

Fixed, committed (`eb06209`), and the dev server has been **restarted with the fix** — both healthy again (app `:5173` → 200, agent `:8787` → listening).

**What was happening** — three facts stacked into the loss:

1. Pi persists an assistant message to the session file **only at completion** (`SessionManager.appendMessage` fires on `message_end`, never during streaming).
2. The client correctly drops live message events for sessions it isn't viewing — so the `message.started` for the in-flight reply is gone by the time you come back.
3. `resumeSession` re-opened the session file from disk even for a session that was live and streaming in memory.

Result: the rebuilt view omitted the reply entirely, and every remaining delta, tool event, and `message.completed` referenced a translator-minted id (`message-N`) that `findMessage` couldn't find — all silently no-oped. The message existed only on disk after completion; the UI never showed it without a manual re-switch.

**The fix**: `resumeSession` now splices the live partial assistant message into the snapshot when the target session is active and streaming. `ActiveSession` keeps its `PiEventTranslator`, which exposes `activeAssistantMessageId` — the exact id the remaining deltas will use — and `inFlightAssistantView` converts the agent-state message (text, reasoning, running tool calls) into a proper `ConversationMessage` with `complete: false`. So the view converges with the live stream: remaining deltas append, tool results attach by call id, completion marks it done. If the stream finished while you were away, nothing is spliced (the translator clears the id at `message_end`) and the persisted message wins.

Four regression tests cover the splice (text+reasoning, running tool calls, the between-messages gap, and the settled stream); the same 19 pre-existing failures are the only ones elsewhere.

You can retest now: start a reply, switch to another thread, switch back — the partial reply should be there and keep streaming to completion.
