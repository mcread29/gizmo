## assistant

It was not the refresh itself, and not the CSS. It is a pre-existing gap in how the virtual message list gets told about size changes, and the refresh put you in the one state where it shows.

**What I measured.** After the reload, rows 51 to 54 in the transcript had stale vertical positions. Row 52 was placed 20px above row 51 and the two reasoning blocks overlapped their neighbours. The positions stayed wrong for several seconds and a scroll nudge did not fix them. They snapped into place only when the next streamed message added a new row.

**Why.** The list uses TanStack Virtual. Its Svelte adapter only pushes a new value into the store when the virtualizer's `onChange` fires, and the core only fires that when the visible range or the scrolling flag changes. A row that grows while its reasoning streams in is re-measured by the core's own resize observer, which updates the later rows' start offsets internally, but nothing tells Svelte to re-render those offsets. The adapter's own source has a comment acknowledging the same hole for count changes and works around it only inside `setOptions`.

**Why the refresh exposed it.** Normally you are following the output, and the list's pin-to-end loop keeps issuing scrolls, so the range keeps changing and the store keeps updating. After the reload the transcript replayed while the run was still going, you ended up scrolled above the bottom with the "1 new message" pill showing, and with no scrolling happening the stale offsets had nothing to flush them.

**The fix** is small and lives in `apps/app/src/lib/features/conversation/MessageList.svelte`: attach a resize observer per mounted row that re-measures the node and then forces a store update, so a growing row always re-renders the rows below it. Want me to make that change?
