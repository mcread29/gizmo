## assistant

Yes—this should come first. It would immediately make existing Pi extensions substantially more useful in Gizmo, before replacing Gizmo’s extension backend.

## Core approach

Keep the in-process `AgentSession`, but bind extensions with a real browser-backed `ExtensionUIContext`:

```ts
await session.bindExtensions({
  mode: 'rpc',
  uiContext: createGizmoExtensionUIContext(sessionId),
  onError: reportExtensionError,
});
```

This does **not** mean switching Gizmo to Pi’s RPC runtime. We would only use `"rpc"` as the extension mode because it correctly communicates:

```ts
ctx.hasUI === true
ctx.mode === 'rpc'
```

Gizmo remains in-process with its existing protocol and shell.

## Browser UI bridge

Each `ctx.ui` call becomes a session-scoped protocol event:

```text
Pi extension
    ↓ ctx.ui.confirm()
GizmoExtensionUIContext
    ↓
session.extensionUi.request
    ↓ WebSocket
AgentStore extension UI state
    ↓
Svelte component
    ↓ user response
session.extensionUi.respond
    ↓
Promise returned to extension
```

Example wire request:

```json
{
  "type": "session.extensionUi.request",
  "sessionId": "abc",
  "request": {
    "id": "ui-123",
    "method": "confirm",
    "title": "Delete checkpoint?",
    "message": "This cannot be undone.",
    "timeout": 10000
  }
}
```

Unlike Pi’s existing RPC implementation, Gizmo can support most of the methods that RPC currently treats as no-ops.

## Widget representation

Pi supports both text widgets and terminal component factories:

```ts
ctx.ui.setWidget('key', ['Line 1', 'Line 2']);
ctx.ui.setWidget('key', (_tui, _theme) => new Text('Custom'));
```

Text widgets can render natively.

Terminal component factories cannot become DOM components directly. They create `@earendil-works/pi-tui` objects that render terminal cells and consume terminal input.

I would support them in three tiers:

1. **Text arrays:** full native web rendering.
2. **Simple Pi TUI components:** compatibility renderer to formatted/preformatted web content.
3. **Interactive/custom TUI components:** explicit unsupported fallback with optional custom web companion.

Trying to recreate the entire terminal renderer, focus manager, keyboard dispatcher, overlays, and cell-based layout in the browser would effectively embed a terminal emulator inside Gizmo. It would work poorly with Gizmo’s visual system.

## Custom UI

Pi’s:

```ts
await ctx.ui.custom((tui, theme, keybindings, done) => ...)
```

cannot accept a Svelte component because existing Pi extensions expect a terminal `TUI`.

I would add a parallel web-native mechanism later:

```ts
await gizmo.ui.custom({
  component: MyWizard,
  props: { repository },
  presentation: 'dialog'
});
```

But it should be optional. The extension’s normal Pi tools, commands, hooks, and basic `ctx.ui` calls remain authoritative.

For existing `ctx.ui.custom()` calls:

- Return `undefined` initially, matching RPC behavior.
- Optionally show a notification explaining that the terminal-only interface is unavailable.
- Eventually allow a browser companion to register a replacement keyed by extension and custom UI ID.

## State model

Add an `ExtensionUIStore` separate from `AgentStore`:

```ts
class ExtensionUIStore {
  dialogs = $state<ExtensionDialog[]>([]);
  notifications = $state<ExtensionNotification[]>([]);
  statuses = $state<Record<string, ExtensionStatus>>({});
  widgets = $state<Record<string, ExtensionWidget>>({});
  working = $state<ExtensionWorkingState>();
}
```

State should be scoped by:

```ts
{
  sessionId,
  extensionId,
  key
}
```

This prevents two extensions both using `"status"` or `"widget"` from overwriting one another.

## Important Pi change

Pi currently gives the runtime one shared `ExtensionUIContext`; calls such as:

```ts
ctx.ui.setStatus('build', 'Running')
```

do not tell the UI context which extension made the call.

For robust browser UI, we need attribution. The clean change would be for Pi’s runner to provide a scoped UI context:

```ts
uiContext.forExtension(extension.sourceInfo)
```

Or include source information with every request:

```ts
interface ExtensionUIRequestContext {
  extensionPath: string;
  sourceInfo: SourceInfo;
}
```

That gives Gizmo:

- Stable ownership
- Per-extension cleanup
- Trust/provenance display
- Correct behavior after reload
- Protection against key collisions

This is a small, generally useful Pi SDK improvement.

## Lifecycle rules

On session reload, switch, fork, disconnect, or deletion:

- Cancel unresolved dialogs.
- Clear extension statuses and widgets.
- Abort pending UI promises.
- Ignore late browser responses.
- Dispose web components.
- Rebuild UI state from the new extension runtime.

Notifications can survive briefly as toasts, but interactive state must not cross runtime replacement.

## Recommended implementation order

1. Add attributed `ExtensionUIContext` support to the Pi patch.
2. Bind Pi extensions in `"rpc"` mode with Gizmo’s custom UI context.
3. Add request/response protocol types.
4. Implement confirm, select, input, and editor.
5. Implement notifications, statuses, and text widgets.
6. Connect editor text, paste, working state, and tool expansion.
7. Connect themes.
8. Build `@gizmo/extension-ui` browser component library.
9. Add optional browser replacements for terminal-only `custom()` interfaces.
10. Then migrate individual Gizmo extensions onto Pi backends.

That gives us broad compatibility first without prematurely redesigning every existing Gizmo extension.
