## assistant

Fixed. The problem was that eviction (`pool.remove` → `#evict` → `session.dispose()`) disposed the raw Pi `AgentSession`, which never fires the `session_shutdown` event the journal extension needs to record the un-recorded tail — so deleting a thread dropped everything since its last journal segment.

## What changed

**`pi-agent-types.ts`** — added an optional `shutdown?(): Promise<void>` to `PiSessionLike`: emits `session_shutdown` to extensions while the extension context is still alive; the caller disposes afterwards.

**`pi-session-factory.ts`** — implemented `shutdown` on the real session, mirroring what pi's own `AgentSessionRuntime.dispose()` does: `runner.hasHandlers('session_shutdown')` → `runner.emit({ type: 'session_shutdown', reason: 'quit' })`. The journal extension's existing handler then records the tail with trigger `session-end`, deduped by entry id, so no double-journaling can occur.

**`session-runtime-pool.ts`** — `#evict` is now async: it drops the map entries synchronously first (so a concurrent sweep or re-activation can't touch the dying runtime), then awaits `session.shutdown?.()` before `dispose()`, and still disposes even if the flush throws (logged via `console.error`). This covers **all** eviction paths — delete, idle sweep, and capacity eviction — not just delete.

**`session-operations.ts`** — `deleteSession` now awaits `pool.remove` before `repository.delete`, so the journal flush completes before the transcript is archived.

**`pi-agent-service.ts` / `websocket-server.ts`** — `dispose()` is now async and awaited in the server-close chain, so journal flushes finish before shutdown rather than racing process exit.
