## Don't build extraction next

The instinct is to go straight to the knowledge layer. I'd resist it, because right now you have 9 MB of history that *nothing reads* — including the agent. Two consequences:

- You'd be writing a reconciliation prompt with no feedback signal, guessing at which facts matter.
- You'd have no way to tell whether a wrong answer came from bad extraction or bad retrieval.

## 1. `journal_search` — retrieval before extraction

One tool: lexical search across segments, returning matching excerpts with segment ids. Maybe 100 lines. It makes the corpus useful the same day, and more importantly it *generates the evidence* for what the knowledge layer should extract: you'll watch which questions the journal answers well and which fall flat, and that's your extraction spec.

9 MB greps in milliseconds, so no FTS, no SQLite. Deferring that was the right call and stays right for a while.

## 2. Chunking — and it has to come before extraction

This moved up my list once I saw the distribution. A fact citing segment `0017` currently points at a **1.6 MB file** — that's not evidence, that's a haystack. Since facts cite segment ids permanently, chunking after extraction means rewriting citations.

Split on turn boundaries at ~40 KB. That turns the largest session into ~40 addressable units and makes "why did we decide this" resolvable to something a person can actually read.

## 3. The small debts (~an hour)

- `pnpm --filter … backfill` runs with the package as cwd, so it targets the wrong workspace.
- `rebuildIndex()` + a frontmatter parser, making `index.jsonl` a genuinely disposable cache rather than a second source of truth.

## 4. Then the knowledge layer

With retrieval in place and segments addressable, build reconciliation as designed: `facts/*.md`, `KNOWLEDGE.md` injected via `before_agent_start`, the `{create, update, supersede, merge}` diff.

**The backfill gave you something valuable here that's easy to miss:** 6,400 real messages is a test corpus. You can iterate the reconciliation prompt entirely offline — run it over segments, read the facts it produces, tune — without waiting for live sessions or burning turns. That's the difference between tuning this in an afternoon and tuning it over weeks.

## One caution

You now have 9 MB of transcripts on disk. Tool *output* is truncated, but tool *arguments* aren't, and neither is prose — so anything you pasted into a conversation is in there verbatim. It's gitignored, so this is a local-disk question, not a leak. Worth one `rg` for key-shaped strings before you point any model at it, and worth the `memory_write` guardrail when facts start getting written.

My concrete suggestion: **`journal_search` plus chunking, together.** They're both small, they're both prerequisites to the knowledge layer being any good, and together they turn the journal from an archive into something that answers questions today. Want me to build them?

## Two tiers

Mirror `resourceRoots()` (`resource-paths.ts:53`), which already establishes the global-then-project precedence chain for skills, prompts, and AGENTS.md:

```
~/.gizmo/memory/              global  — facts about the user
  facts/  KNOWLEDGE.md
  journal/                    ← only for sessions with no project

<project>/.gizmo/memory/      project — facts about this codebase
  facts/  KNOWLEDGE.md  journal/
```

The asymmetry is deliberate: **the journal is inherently project-scoped** — it records work done in a workspace. The global journal exists only to catch sessions rooted outside any project (you have 43 of those at `C:\Users\mchan`). The *facts* layer is where two tiers genuinely earn their keep.

Three rules make it work:

1. **The fact's type picks the tier.** `user` / `feedback` → global; `project` / `reference` → project. The reconciliation pass already has to classify, so this is free.
2. **Project wins on conflict.** Same precedence as skills. A project can override a global preference without deleting it.
3. **Promotion is allowed.** A session in project A must be able to write a global fact — that's how "prefers tabs" gets learned once instead of twenty times. It's the rule most two-tier designs miss, and it needs to be explicit in the extraction prompt.

Recall reads both and merges, tagging each line with its tier so the model knows a global fact is a user preference rather than a codebase truth.

## The tradeoff you'd be accepting

Right now memory is bundled into `pi-session-factory.ts`, so it is **always on**. As a discovered extension it becomes toggleable per project via `ProjectCatalog.disabledPiExtensionsFor()` and the `gizmoExtensions` overrides in `.gizmo/config.json`.

That cuts both ways. You get real UI, independent versioning, and installability — and memory becomes something that can be silently off for a project, which means a gap in the journal you won't notice until you go looking for history that isn't there. Given the journal is supposed to be the authoritative layer, that's a genuine cost.

Two ways out: install it as a **global** extension in `~/.pi/agent/extensions` (project-local `.pi/extensions` load only after project trust, which would be a worse failure mode), or keep the Pi hooks bundled and ship only the tools/UI as the extension. I'd start with the first — global scope, one place to enable, and you keep the single-package story.

There are two different payloads here:

| | What it is | Changes | Needs to be |
|---|---|---|---|
| `KNOWLEDGE.md` index | **data** — which memories exist | every fact write | always present |
| How to use memory | **behavior** — when to search, how to write a fact | ~never | present at the moment of use |

Conflating them is how these systems end up either paying a permanent token tax or having a model that never calls the tools.

## The index → system prompt

This one has no alternative. A skill can't carry it, because skills load on demand and the model can't know to load a memory skill if it doesn't know memories exist. Bootstrapping problem: the index is the thing that tells it there's anything to retrieve.

So: `before_agent_start`, appending to `event.systemPrompt`. Note that in gizmo this is the *only* route — the factory sets `systemPromptOverride`, which replaces Pi's prompt wholesale, so `buildSystemPrompt`'s `appendSystemPrompt` is unreachable. Chaining onto `event.systemPrompt` is the seam.

Cache cost is fine here: `KNOWLEDGE.md` only changes when a fact is written, which is rare. Per-turn *recall* is a different thing and belongs in the `context` hook, not the prompt.

## The behavior → tool guidelines first, skill second

Start with what Pi already gives you for free — `promptSnippet` and `promptGuidelines` on the tools themselves. Gizmo already uses this for `run_script` (`run-script-tool.ts`), and Pi folds them into the system prompt's `Available tools` and `Guidelines` sections automatically, only while the tool is active:

```ts
promptSnippet: 'Search recorded conversation history for prior decisions',
promptGuidelines: [
  'Use journal_search when the user refers to a past decision or asks why something is the way it is.',
  'Use memory_write when you learn something that will still matter in a future session.',
],
```

Watch the naming rule Pi's docs call out: guidelines are appended flat with no tool-name prefix, so each one must name its tool. "Use this tool when…" is useless when five extensions contribute bullets.

That's ~40 tokens and covers the common case: *know the tools exist, know roughly when to reach for them*.

Then a **skill** for the part that's genuinely long and rarely needed: the fact-writing style guide, the supersede-vs-merge policy, tier placement rules (global vs project), the don't-store-secrets rule with examples. That's easily 500–800 tokens of policy that matters only in the seconds after the model decides to write a memory. Paying for it on every turn of every session is exactly the tax skills exist to avoid.

## The split in numbers

- Always resident: index (~200–400 tokens at your current scale) + tool guidelines (~40)
- On demand: `memory-writing` skill (~600), loaded only when actually writing

Versus putting it all in the system prompt: ~1,000 tokens × every turn × every session, to change behavior that fires a few times an hour.

## One wiring note

You're built-in rather than an extension now, so a bundled skill needs its path appended to `additionalSkillPaths` in `pi-session-factory.ts` — the same move I made for `additionalExtensionPaths` with `journalExtensionPath()`. It won't be discovered on its own, since the factory sets `noSkills: true` and supplies the list explicitly from `catalog.enabledSkillPaths(cwd)`.

Add the index injection when the facts layer lands, since there's nothing to index yet. Write the skill last, once you've watched the reconciliation pass make mistakes and know what the policy actually needs to say.

### Exposure — do not skip this

`pi-session-factory.ts` sets `systemPromptOverride` whenever an active Gizmo extension supplies a

silently breaks in the override case.

## Pitfalls hit while building this layer

- **Don't put Windows paths in bash heredocs.** Backslashes collapse even in quoted heredocs,
  producing drive-relative paths and silent zero-result runs. Pass paths via `process.cwd()` or argv.
- **Prettier reflows unions and call signatures**, which breaks blind string-replace edits. Assert
  every replacement, or use the Edit tool.
- **`getBranch()` vs `getEntries()`**: the latter includes retried/abandoned siblings and imports as
  duplicated prose. The journal uses `getBranch()` deliberately.
- **Verify tool loading through the real path.** `resourceLoader.loadExtensionFactories()` is *not*
  the load path and returns empty; the real result lands in `extensionsResult` after `load()`.
