| Claude Code | Maps to | Count |
|---|---|---|
| `assistant:tool_use` (`id`,`name`,`input`) | my `toolCall` | 1,922 |

Two pieces of luck: `toolCallArguments()` already probes `input`, and the thinking block already uses the key `thinking`. So the adapter is essentially entry-shape translation.

The one thing that would go badly wrong if unhandled: Claude Code puts tool results in **`user` messages**, so a naive import would journal 1,921 tool payloads as *user prose* — poisoning exactly the signal the knowledge layer cares about. The adapter has to split those into `toolResult` role.

## Idempotency comes free

Both formats have stable per-entry ids (Pi entry ids, Claude `uuid`). If I use those as the entry ids, `resumeAfter()` dedupes on re-run — so backfill is safely repeatable and can't double-import.

I'd also stamp each backfilled segment with `source: pi-archive | claude-code` in its frontmatter, so when the knowledge layer starts extracting you can tell which facts came from imported history versus live sessions.
